# 35 要不要拆成多个 Agent

比较 AtlasButton 1.4 与 2.0，看起来天然能分给两个 Agent：一个读旧版，一个读新版，再由第三个汇总。可是目前只有两张短卡片，固定并行读取已经能完成同样的事。若每个 Agent 都重新解释任务、选择工具和生成总结，可能只是增加了三次丢失约束的机会。

这一篇是选读决策篇。目标不是实现多 Agent，而是设计一场能决定“是否值得拆”的实验。

## 三种方案要解决同一任务

先固定输入：当前用户为 `reader-a`，比较 1.4 与 2.0 的等待参数，资料仅 C-B14 与 C-B20，要求说明点击控制边界，不执行修改。

| 方案 | 谁决定工作分配 | 合并时拿到什么 |
| --- | --- | --- |
| 单个受限 Agent | 一个循环选择资料与步骤 | 同一任务状态中的证据和结果 |
| 固定并行 | 程序把两个版本的读取并行发出 | 原始资料与确定的版本标签 |
| 多 Agent | 子任务各自选择步骤，再交给协调者 | 子任务结果、证据、状态与用量 |

不能让单 Agent 只拿一张卡，而多 Agent 拿全部资料，再宣布后者更好。三个方案必须使用同样的身份范围、题集、资料快照、工具预算和判断标准。若模型配置不同，也要明示，避免把模型差异误认为架构收益。

## 可独立检查，比角色名称更重要

“研究员、批评家、专家”只是名字。可以独立检查的子任务应该有明确输入与输出，例如“只核对 C-B14 的等待参数，返回字段名、行为、引用和未知”。汇总者必须收到原始引用，而不是仅收到一句“旧版用 loading”。否则子任务丢掉 `disabled` 的区别，汇总者很难恢复。

对于 Q14 的同版本冲突，尤其不能让两个子任务各自读一份资料后输出肯定答案，再按投票选胜者。事实冲突需要看来源与适用范围，两个模型意见相同也不会让文档变得一致。

可以先写一个未执行的子任务合同：

```ts
type ReviewResult = {
  taskId: string
  scope: { component: 'AtlasButton'; version: '1.4' | '2.0' }
  claims: Array<{ text: string; sourceId: string; revision: string }>
  unknowns: string[]
  status: 'complete' | 'insufficient_evidence' | 'failed'
}
```

这个结构仍需事实检查。它的好处是汇总层知道什么缺了，不会把“子任务未完成”当作“该版本没有差异”。

## 并发会改变成本与失败形态

两个分支同时运行，理想情况下缩短等待时间；但整体还需要等慢分支、处理重试并做汇总。其总调用消耗通常是各分支加协调开销，不是墙钟时间短就更便宜。观察时既记录总任务耗时，也记录各分支耗时、费用或未知用量，以及人工接管次数。

权限也不会因为拆分而放松。每个子任务只能得到本次需要的授权资料，不能把主任务所有上下文广播给所有角色。共享内存若没有范围控制，会让分支间接读到原本不该看到的信息。子任务的工具结果和自然语言总结都属于待校验数据，不能覆盖协调者的系统约束。

协调失败还有一种常见表现：一个分支超时，汇总者为了显得完整补出缺失版本的行为。正确做法是明确部分完成，或者按预算重试只读分支。不能因为多 Agent 看起来适合“互相纠错”，就省掉执行端校验。

## 先制定撤回条件

实验题集至少包括正常双版本比较、缺一侧资料、同版本冲突、越权请求和一个慢分支。对同一批合成任务分别记录任务通过率、禁止行为、工具调用正确性、耗时、消耗和人工接管。若采用真实模型，应重复运行，保存运行版本与样本数；本篇没有运行模型对比，也没有给出收益数字。

在实验之前写下决策规则：安全回归出现新增失败就停止推广；质量相同而协调成本上升，保留固定并行；只有动态分工带来可重复的任务收益，才在那些任务上开放多 Agent。阈值应根据真实使用目标确定，不能从别人的演示抄一个百分比。

对于当前两张按钮卡片，选择固定并行或单流程是一个合理的教学判断，不是系统不够先进。未来资料跨多个可独立核验的来源，才有重新实验的理由。架构的价值由任务结果证明，不由角色数量证明。
