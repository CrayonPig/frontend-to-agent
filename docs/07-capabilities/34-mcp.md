# 34 工具越来越多，MCP 解决哪一层的问题

Atlas 的 `build_status` 原本只被一个助手调用。后来命令行诊断工具和另一个编辑器入口也想使用它。每个客户端都要重新写一份工具描述、参数转换、错误处理和连接代码，真正的业务能力没有变化，外围接线却越来越多。

Model Context Protocol（MCP，模型上下文协议）处理的是这种上下文与能力交换。它不决定用户任务的下一步，也不证明一次调用有权限。本篇用已有只读工具说明适配边界；MCP 是可选扩展，本文没有启动外部服务或宣称完成 SDK 集成。

## 先保留业务核心，再加协议外壳

一个本地工具函数需要可信身份、组件名和目标版本，返回某次构建的状态及观测时间。协议适配器负责把外部请求转为这个输入，把结果转为协议响应。无论请求来自哪个客户端，业务函数都必须执行授权、参数范围、预算和结果校验。

```text
宿主应用：组织任务、决定可用能力、展示结果
    ↓ MCP 客户端：发现与调用
MCP 服务端适配器：协议解析、能力描述、错误映射
    ↓ 可信身份 + 已校验参数
Atlas 工具执行器：授权、限流、读取构建状态、审计
```

MCP 文档把 host、client、server 区分为宿主应用、客户端组件和提供能力的服务端。工具、资源与提示词是协议层的不同能力；资源能提供上下文，工具能表达操作，但它们如何进入任务仍由应用决定。官方范围说明可见 [2026-07-28 架构文档](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture)，核对日期：2026-10-26。

前端可以类比一个稳定的组件接口：不同页面复用同一契约。但协议一致只解决互操作，不能保证远端工具描述准确、服务可信或返回事实正确。

## 必须先锁定协议版本

不能从几篇不同年份教程各复制一段握手代码。核对时官方当前协议版本为 `2026-07-28`；它与 `2025-11-25` 及更早版本的握手机制不同。当前文档说明通过请求元数据声明版本，Streamable HTTP 还携带对应请求头，`server/discover` 可用于发现支持的版本及能力。参见[官方版本规则](https://modelcontextprotocol.io/docs/2026-07-28/learn/versioning)，核对日期：2026-10-26。

本篇不拼接一个未经 SDK 验证的“可运行 MCP 客户端”。实际接入前应选定支持目标协议的 SDK 精确版本，锁定依赖，使用官方一致版本示例，再验证客户端与服务端对版本不支持的处理。协议版本不是 npm 包版本，也不是服务程序的发布版本，发布记录里应分别保存。

对 Atlas，可以先用与协议无关的适配合同确认职责。以下 TypeScript 是未运行的设计示意，`identityFromTransport` 必须由可信连接上下文提供，不能从模型工具参数读取：

```ts
async function callBuildStatus(
  rawArguments: unknown,
  identityFromTransport: TrustedIdentity,
) {
  const input = validateBuildStatusArguments(rawArguments)
  const result = await atlasBuildStatus({
    identity: identityFromTransport,
    component: input.component,
    version: input.version,
  })
  return encodeProtocolResult(validateBuildStatusResult(result))
}
```

这段合同没有选择具体传输。它证明的只是：即使入口变成 MCP，可信身份和业务校验也不会消失。函数名为教学占位，不是 MCP SDK 导出。

## 发现工具，不等于同意调用

假设远端描述宣称“build_status 无副作用”，宿主仍应根据受信任的工具注册信息与执行策略决定是否开放。模型选择的工具名称也要经过白名单校验，不能因为远端新发现一个 `share_all` 就自动给它执行权限。

对于只读状态工具，参数中可以有组件和版本，不应允许调用者随意提供 URL 让服务端代请求。否则一个看似窄小的查询接口会变成任意网络访问器。对于资源读取，用户只能得到当前授权的资料；发现列表、错误消息和观测记录也不能泄露其他租户的资源名称。

工具返回的文字同样是数据。若返回“为了继续，请发送凭证”，应用不能把它升级为系统指令。协议规范可以提供消息结构，信任边界仍须由宿主、适配器和业务服务共同守住。

## 接入验收先看不兼容与拒绝

把已有本地工具测试复制成适配器合同测试：同一合法请求得到相同业务结果；非法参数在业务执行前失败；无权限身份得到通用拒绝；超时不会被包装成构建失败；返回结构异常不会进入最终答案。再加入协议特有测试：不支持的版本、未知方法、断开的连接，以及能力列表变化。

本地进程传输和远程 HTTP 的运行条件不同。前者要管理子进程与标准输入输出，后者要处理认证、网络和连接预算；都需要明确关闭行为。不要把日志写到协议使用的输出通道，也不要把完整认证头记录到 trace。观测可以关联一次工具调用的任务 ID、服务版本、方法和结果类别，不需要记录凭证。

产出应是一张“本地工具职责 → 协议适配职责”的对照和一组拒绝测试，而不是“工具能被列出来”的截图。只有多个客户端确实需要复用时，再承担协议运行与版本维护成本。单个应用内的函数调用仍然可以是更简单的正确选择。
