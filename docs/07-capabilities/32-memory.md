# 32 这次任务的状态，和下次还要记住的信息

用户连续三次要求“迁移建议用表格展示”，助手每次都重新询问格式，确实显得笨拙。但如果为了省一次询问，把对话全部写入长期存储，又会把过时版本、一次性的猜测和敏感数据带到下一次任务。

记忆不是聊天记录换一个数据库。它是一条会影响未来行为的数据，必须说明为何保存、适用于谁、什么时候失效，以及如何撤销。本篇只设计最小生命周期，不为 Atlas 增加一个无边界的“自动记住一切”。

## 三种数据有不同的责任

任务状态回答“这次做到哪里”：例如草稿已预览、尚未确认，恢复后要核对哪个操作。会话历史回答“刚才说过什么”：例如用户从 1.4 问到 2.0。长期记忆回答“下次仍有理由使用什么”：例如用户明确选择默认用表格展示迁移差异。

前两者即使存了很久，也不会自动成为第三者。一次问“1.8 是否支持 loading”，不代表用户项目永远使用 1.8；一次工具调用超时，更不能记成“该组件不可用”。任务状态的可靠恢复在第 28 篇已经解决，长期记忆不能代替操作回执或确认记录。

前端的用户偏好设置是一个有用入口：用户可以保存主题、语言，也可以修改。类比失效处在于，模型可能从一句话推断出没有明确表达的偏好。推断容易变成隐藏状态，用户却不知道以后为什么总得到某类答案。

## 从一条可撤回的偏好开始

下列结构是未运行的设计示意，时间和标识全部合成：

```ts
type PreferenceMemory = {
  id: string
  tenantId: string
  userId: string
  key: 'migration.outputFormat'
  value: 'table' | 'paragraph'
  source: { kind: 'explicit_user_preference'; eventId: string }
  revision: number
  validUntil: string
  state: 'active' | 'revoked'
}
```

它刻意不允许任意“事实”作为 value。这个存储只管理呈现偏好，不能写入“AtlasTable 支持百万行”或“用户有 demo-bay 权限”。权威组件事实仍来自有版本的文档；权限仍来自可信身份和服务端策略。缩小可以保存的内容，往往比添加一条“请谨慎记忆”的提示词更有效。

一个最小流程可以这样演练：用户明确说“以后迁移建议用表格”，服务端把候选偏好展示出来，按产品约定获得保存授权后写入 `revision: 1`；下次同一租户、同一用户发起迁移任务，读取仍有效的偏好；用户说“改成段落”时用条件更新把版本推进到 2；用户删除偏好时标记撤销，并让缓存与检索副本失效。

是否每次显示确认，是产品对这类低风险偏好的设计选择；但保存范围和删除入口必须让用户可知。有敏感含义的信息不能沿用这个轻量流程。本文没有授权收集真实用户偏好，全部只在合成场景里演练。

## 读取前要问四件事

第一，这条信息属于当前租户和用户吗？查询条件必须含两者，不能先读取所有记忆再让模型筛选。即便某个偏好看起来无害，也不能把跨用户复用变成默认行为。

第二，它还有效吗？过期时间表达的是应用允许使用的窗口，不证明内容一定正确。当前用户明确要求段落时，应优先遵循本次要求，并按产品规则决定是否更新偏好，而不是让历史压过当前任务。

第三，它与任务有关吗？用户喜欢表格，不代表解释一个布尔参数也要输出一张大表。记忆是可用的上下文，不是必须执行的流程。

第四，它的来源足够可靠吗？“用户明确设置”与“模型从历史推断”应分开。若以后确实需要推断式记忆，应有单独类别、置信与核实机制，不能把来源字段统写成“已知”。本篇设计直接排除推断式写入，减少无法验证的行为。

## 冲突和删除都要跨越缓存边界

假设两个设备同时把偏好从版本 1 修改：A 写成段落，B 写成表格。只按最后到达时间覆盖，会让迟到请求覆盖更新意图。可使用 `expectedRevision` 条件更新；版本不符时返回冲突，让调用方读取最新值后决定。这里可以复用前端处理乐观更新的经验，但不能用 UI 的最新状态推断服务端已持久化成功。

删除也不只是删一行。若答案缓存已经把偏好纳入生成，后续命中是否允许继续使用旧结果，需要明确策略；如果记忆建立了向量索引，副本也要删除。审计记录可以保留“某条合成偏好在何时被撤销”的最少事件，不能为了审计永远保留被要求删除的原文。真实系统还应定义保留期、访问权限和删除完成的确认方式。

## 本地实现验证到哪里

`examples/atlas/governance.mjs` 的 `MemoryStore` 是内存教学实现，只覆盖身份隔离、来源字段存在、过期与删除；它没有实现上述偏好白名单、条件修订更新、用户确认界面或持久化。不要把设计要求误认为已有运行保证。在仓库根目录执行以下独立示例：

```bash
node --input-type=module <<'JS'
import { MemoryStore } from './examples/atlas/governance.mjs'
import { principal } from './examples/atlas/fixtures.mjs'
const memory = new MemoryStore()
memory.put(principal, { id: 'format', value: 'table', source: 'demo-explicit-1', expiresAt: 100 })
console.log(memory.read(principal, 'format', 50)?.value)
console.log(memory.read({ ...principal, userId: 'reader-b' }, 'format', 50))
console.log(memory.read(principal, 'format', 100))
memory.delete(principal, 'format')
console.log(memory.read(principal, 'format', 50))
JS
```

预期依次输出 `table`、`null`、`null`、`null`。这里传入合成时钟，没有保存真实偏好；程序退出后内存清空。

## 做一次生命周期回归

用 `reader-a` 和另一个合成用户运行或手工重放以下序列：保存表格偏好、读取、同租户另一用户读取、过期后读取、更新冲突、撤销后读取。预期分别为可用、可用、不可见、不可用、拒绝陈旧写入、不可用。再加入一个恶意文档，要求把“拥有另一租户权限”写入记忆，执行端必须拒绝不在白名单中的 key。

留下记忆 ID、修订、来源事件、读取或失效原因即可。不要把整段聊天或私密推理当作审计字段。验收这次设计时，应能回答谁创建了记忆、为何影响当前回答、用户如何改正它，以及撤销后哪些副本不再使用。

只有这些问题都有答案，长期存储才是可管理的能力。否则它只是让一次错误活得更久。
