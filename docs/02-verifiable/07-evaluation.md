# 07 答案看起来不错，怎么判断真的变好了

改完 Prompt，Q03 终于回答了 `loading` 和 `disabled`。如果只记住这次成功，就很容易宣布新版更好；但同一修改可能让 Q05 开始编造虚拟滚动，或让 Q08 的拒绝文字泄露隐藏资料。一次演示只能展示一个结果，不能证明修改后的整体行为。

第 02 篇已经准备了 14 道题和依据。本篇把它们变成可以重复执行、找到具体失败的检查流程。第一份基线的目的不是拿到漂亮分数，而是让下一次修改有可比较的起点。

## 把题目、答案和判定规则分开放

题目包含用户问题、可信身份、目标版本和允许资料；候选答案来自被测实现；判定规则由题目依据决定。若把标准答案一起传给模型，再以复述程度评分，测到的主要是复制能力。

```ts
// 评测记录契约示意，不是向模型发送的输入。
type CaseSpec = {
  id: string
  fixtureVersion: string
  split: 'development' | 'check'
  expectedKind: string
  requiredFacts: string[]
  forbiddenBehaviors: string[]
}
```

Q03 的关键事实是 1.4 使用 `loading` 显示等待、另用 `disabled` 阻止 click；禁止行为是推荐 `pending` 作为 1.4 参数。Q05 的预期则是明确资料不足，不能把未知判成“不支持”。Q08 的标准来自服务端身份与隔离规则，不是读取 T-B20 后比较秘密内容。

Q14 使用冲突夹具替换 C-T20，Q09 才加入 X-T20；这个输入条件也属于测试定义。把所有卡片一股脑发给所有题，会改变原来的题意。每次运行应保存实际资料修订列表，不能只保存一个题号。

## 一份答案至少有四种分数

格式检查回答能否按契约解析；事实检查结论是否被资料支持；任务完成检查是否满足用户全部要求；拒答检查是否在该答时答、该保留未知时保留未知。四者相关，但不是同一个布尔值。

| 候选结果 | 格式 | 事实与范围 | 任务判定 |
| --- | --- | --- | --- |
| Q03 返回合法 JSON，却推荐 pending | 可通过 | 失败 | 失败 |
| Q05 明确无法确认虚拟滚动 | 可通过 | 保留未知 | 通过 |
| Q12 只回答默认 coarse，跳过精度问题 | 可通过 | 已回答部分正确 | 不完整 |
| Q08 拒绝，却复述隐藏租户内容 | 可通过 | 越权披露 | 失败 |

因此 `resultKind: 'answered'` 是被测实现的声明，`verdict: 'pass'` 是评价结果。不能把前者复制给后者。链路无异常也不是任务通过的依据；trace 只能提供发生过的动作与输入输出证据。

## 自动检查擅长什么，在哪里停

先自动检查结构、允许的类别、引用集合和工具动作。对于这组范围有限的 fixture，可以增加规则检查关键事实与禁止行为，但别把关键词匹配包装成通用事实裁判。

例如判断答案是否包含 `pending` 会误伤“1.4 不支持 pending”。反过来，答案同时出现 `loading`、`disabled`，也可能说它们“不需要设置”。字符串完全相同更不合适：两种正确表述可以用不同句式。规则应解释自己的覆盖范围，剩余部分交给人工核对。

人工评阅也需要标准。先确认任务范围，再逐条对照关键断言与资料，最后看禁止行为和缺失子问题；写下短理由，例如“引用 C-B20，目标却是 1.4”。不要求获取模型私密推理，也不因为回答长就加分。引入模型裁判之后，仍应保留人工抽查和裁判与人不一致的样例，不能让评分模型成为唯一真相来源。

## 开发题与检查题不能混着用

仓库示例将 Q01–Q08 标为开发题，Q09–Q14 标为检查题，并在报告中分别列出。它们都是公开教学题，不能被称为严格盲测；作者或调试者一旦根据某道检查题修改实现，那道题便参与了开发，应如实记录，并新增独立改写题补充检查。

独立题不必发明新产品事实。例如换一种表达问同一版本的参数，或把 Q12 的两个子问题调换顺序，仍用相同资料核对。但它只能检查表达变化，不能证明系统覆盖了新的组件能力。区分“问题数量增加”与“能力覆盖增加”，会让报告更诚实。

## 第一份报告要能追到那一份答案

最小报告每次保留运行 ID、题目 ID、资料包版本、Prompt 版本、模型/适配器版本、结果类别、结构检查、事实判定、任务判定和简短理由。候选答案文本或受限文件引用必须能找到；否则下一次只能比较分数，无法解释为什么变化。合成数据可以直接保存，真实内容需最小化、脱敏、限权和设置保留期限。

```text
runId: demo-check-001
caseId: Q03
adapterVersion: mock-v1
fixtureVersion: atlas-fixture-01
resultKind: answered
format: pass
facts: fail
task: fail
reason: 把 pending 推荐为 1.4 参数
candidateRef: 本次合成候选答案记录
```

这是失败记录格式示意，不是本次实际测试结果。执行 `node examples/atlas/evaluate.mjs` 可生成仓库中的 mock 报告；它验证的是规则与管道，不是模型真实准确率；实际执行结果以生成的报告与交付验证记录为准。使用真实模型时，在固定输入、版本和参数下做多次运行，分别报告每题的波动及总样本数，不只挑最好的一次。

合格基线还必须包含失败：给 Q03 注入错误版本答案、给 Q08 注入隐藏引用，检查评测是否会拒绝它们。一个永远输出“通过”的测试脚本也会得到 100%，但没有检查价值。可以把它理解为前端测试里的断言敏感性：页面不崩溃，并不证明按钮行为正确。

本篇验收是形成一份可重复运行、能回到候选答案和判定依据的报告，并明确自动覆盖与人工覆盖。分数暂时不高没有关系；知道哪些题失败以及为什么失败，才有依据继续处理下一篇的错误恢复。
