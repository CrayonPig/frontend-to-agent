# 09 超时、重试与并发：哪些请求可以再来一次

一个模型请求偶尔慢，给它加一次重试看起来很合理。问题出在高峰时：原请求还在远端执行，客户端又发一次；每个页面都这么做，调用数量继续增长，排队更长，于是更多请求超时。单个请求的“兜底”最后放大了整个系统的压力。

本篇先处理只读模型调用，建立三个约束：一个任务最多等多久、最多尝试几次、同时允许多少工作。以后进入有副作用工具时，还要额外讨论幂等与结果核对，不能直接复制这里的重试规则。

## 预算属于任务，不属于每次尝试

假设教学策略给任务 8 秒、最多 2 次尝试。这些数字只是方便演示，不是通用最佳实践。第一轮用掉 6 秒，第二轮就只剩 2 秒，不能重新获得完整的 8 秒。排队、退避、校验也会消耗任务时间。

```text
任务开始 ─ 排队 ─ 尝试1 ─ 退避 ─ 尝试2 ─ 校验 ─ 返回
         └──────── 同一截止时间 ─────────────┘
```

实现时用单调时钟计算进程内耗时，保存截止时间或剩余预算，并在每个阶段前重新检查。跨进程恢复不能直接携带本机的单调时钟值，后续需要持久化业务期限和重新计算本地预算。

以下是控制流程伪代码，不是可直接复制的完整重试库：

```ts
for (let attempt = 1; attempt <= maxAttempts; attempt++) {
  assertNotCancelled()
  const remaining = deadline - monotonicNow()
  if (remaining <= 0) throw budgetExceeded()
  try {
    return await callWithTimeout(Math.min(perAttemptLimit, remaining))
  } catch (error) {
    if (!isTransient(error) || attempt === maxAttempts) throw error
    await abortableBackoffWithin(deadline)
  }
}
```

`isTransient` 只能识别适配器明确分类的暂时故障，不能看到任何异常就返回 true。超时控制要真正把信号传给下游支持取消的操作；仅用 `Promise.race` 让等待先结束，不会自动停止后台工作。没有完成取消的工作仍可能占用资源，不能因为本地超时就当作资源已释放。

## 再试之前，先问它为什么失败

暂时连接故障、明确限流、部分可恢复服务错误可以在预算内考虑重试。服务端给出重试等待提示时应尊重，但若等待会越过总截止时间，就停止或告知稍后再试。退避加入随机抖动，避免大量客户端在同一时刻再次拥入。

资料不足、未知版本、权限拒绝、确定的字段错误不属于这类问题。Q06 没有 1.8 文档，调用两次也不会长出 1.8 的事实。把这些结果加入重试，只会让原本清楚的失败变慢且更贵。

输出结构不合格可以有一次独立的修复策略，但应记录为修复尝试，并受同一预算控制；它与传输重试不是同一原因。即使第二次成功，也保留第一次失败，后续评测才能看见代价。

## 并发上限保护的是正在做的工作

浏览器禁用提交按钮可以减少误点，不能限制所有客户端。服务端需要限制同时处理的任务数，也要限制等待队列长度。队列没有上限，内存和用户等待时间仍会无限增长。

一个并发槽位通常在真正开始执行前获取，在任务结束或已确认下游停止后释放。等待槽位也应可取消，并消耗总预算。若网络库不能保证取消后远端停止，应用只能控制本地并发与提交速率，不能把本地槽位数宣称为远端实际执行数。

教学中可以用容量 2、队列 3 的小值观察：同时提交第 6 个任务时，应快速返回受控的繁忙结果，而不是把它悄悄挂在无界队列里。这个实验验证的是背压行为，具体容量仍需依据实际延迟、资源与服务配额确定。

## 超时留下的是未知，不是撤销证明

当前模型请求是只读任务，但超时仍可能留下远端计算和费用。未来调用写工具时，风险会更直接：写入已经成功，回执在网络中丢失，再试一次可能写出两份。

因此日志至少保留任务/请求标识、尝试序号、错误类别、已等待时间、停止原因和已知用量。用量未返回应标未知，而不是 0。后续第 25 篇会把操作 ID、幂等键与查询实际状态加入副作用流程；本篇不能用“模型调用可以重试”推出“任何工具都可以重试”。

## 用一张表验收恢复行为

以下都是故障注入的预期，不是外部服务的实测：

| 注入条件 | 预期尝试 | 预期终态与依据 |
| --- | --- | --- |
| 首次暂时错误，第二次正常 | 最多 2 次 | 预算内完成，保留首次错误 |
| 每次都返回限流且等待超预算 | 不继续无效等待 | 预算耗尽或受控繁忙 |
| Q06 返回资料不足 | 1 次或前置直接返回 | 合格任务结果，不重试 |
| 排队时用户取消 | 0 次模型执行 | 取消，移出队列 |
| 首轮耗尽总预算 | 不发第二次 | 超时，远端结果可能未知 |
| 队列已满 | 0 次模型执行 | 快速拒绝过载，避免无界积压 |

运行本地模拟时要断言实际调用次数，不只检查最终文案。还要验证取消后没有计时器继续发起新尝试、异常路径释放本地资源、失败不会泄露请求内容。测试可以使用可控时钟或很短的合成延迟；报告不能把这类数字写成供应商性能结论。

有了这些约束，一次用户任务已经可能包含排队与多次模型尝试。单行日志很难解释它们的关系，下一篇用 trace 把这些外部可观察动作串起来。
