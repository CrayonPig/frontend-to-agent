# 08 HTTP 成功之后，还有哪些失败

同一个“没有得到答案”，可能来自三条完全不同的路径：模型服务没有响应，模型输出了坏 JSON，或者资料确实没写虚拟滚动。若页面统一显示“系统繁忙，请稍后再试”，用户会对 Q05 反复点击，而重试永远不会凭空补出文档。

错误分类的目的不是增加枚举值，而是决定接下来做什么。一个类别如果不能改变反馈、恢复或调查方向，就未必需要单独存在；反过来，动作明显不同的失败不该被一个 `catch` 压平。

## 把技术失败与任务结果分开

第 05 篇的 `TaskResult` 表示任务能够给出的结果：有依据的回答、资料不足、需要澄清、无权访问、证据冲突和执行不可用。网络超时与输出解析失败则是执行过程出了问题，并不属于“资料不足”。可以在外层响应中区分两者。

```ts
// 响应封套示意；TaskResult 沿用第 05 篇定义。
type ResponseEnvelope =
  | { requestId: string; execution: 'completed'; result: TaskResult }
  | { requestId: string; execution: 'failed'; error: {
      category: 'transport' | 'provider_refusal' | 'invalid_output' | 'internal'
      retryable: boolean
      message: string
    } }
  | { requestId: string; execution: 'cancelled' }
```

这个封套并不意味着每种状态都要用 HTTP 200。请求体不合法、未通过身份认证、资源授权失败，应采用应用约定的 HTTP 语义；已经建立的流式响应则可能只能通过流内错误事件结束。本文关注的是无论如何传输，都不要丢掉可恢复性和任务原因。

模型拒答也要单独处理。供应商的安全拒答不等于本应用完成了权限检查；应用的 `forbidden` 来自服务端授权，不能把模型是否愿意回答当作权限判断。拒答的原始说明还可能包含内部细节，返回页面前应映射为安全文案。

## 同样没有答案，下一步却不同

| 发生了什么 | 检查证据 | 用户下一步 | 系统处理 |
| --- | --- | --- | --- |
| 连接超时 | 调用阶段与剩余预算 | 稍后重试或停止等待 | 按策略有限重试，记录远端结果未知 |
| 输出不是合法结构 | 解析/字段错误类别 | 重试一次或反馈问题 | 可做有界修复，保留失败样本 |
| Q05 缺少虚拟滚动资料 | C-T20 未提供能力说明 | 补充权威资料 | 返回资料不足，不自动重试 |
| Q07 没有目标版本 | 输入缺失 | 选择版本 | 发起澄清，不猜“最新” |
| Q14 两份资料冲突 | 两张同范围资料互相矛盾 | 请维护者核实 | 保留冲突，不任选结论 |
| Q08 请求其他租户内容 | 服务端权限判定 | 使用有权访问的范围 | 拒绝且不披露隐藏资料元数据 |
| Q11 请求执行 share | 当前工具能力边界 | 阅读说明或转到授权操作入口 | 说明未执行，不伪造成功 |

其中资料不足、澄清、拒绝和冲突都可以是正确的应用行为。统计错误率时，应把“基础设施故障”和“用户任务未能获得完整答案”分别统计，否则团队可能为了降低错误数，把正确拒绝改成无依据作答。

## 最难发现的是业务判断错误

坏 JSON 会马上触发解析器；把 `pending` 当作 1.4 参数却可能顺利通过所有技术检查。业务错误需要用第 07 篇的任务标准发现，不能仅依赖异常日志。

想象一次记录：HTTP 成功、结束原因正常、JSON 有效、引用 C-B14。表面上没有故障，但人工发现答案说等待图标会禁止点击。正确的复盘方向是证据遵循，而不是加大超时或重试次数。重试可能偶然得到正确答案，却不能解释为何失败，更不能证明问题被修复。

可以先为失败保存一个短的机器类别，如 `unsupported_claim`，再关联题目 ID 与候选答案。不要在日志里保存任意原始异常对象：请求头、模型输入和服务器路径可能混在其中。页面只展示稳定错误码和安全说明，详细调查记录按权限保存。

## 恢复操作也有自己的边界

对结构错误，可以让模型再生成一次，或用确定性代码修正明确的包装错误。但“修复”不能偷偷改写事实、补出缺少的引用，或无限循环直到格式看起来合格。每次重试都占用同一任务预算，并关联到原始运行。

对于资料不足，恢复动作是获取资料；对于版本缺失，是询问用户；对于权限拒绝，是改变合法访问范围。三者都不应该进入网络重试队列。对于取消，恢复动作通常是用户重新发起，而不是后台替用户继续跑。

还有一种容易被隐藏的情况：观测平台上报失败。它可能影响排查，但不应把已经完成的只读答案改成“生成失败”并重复调用模型。业务执行与遥测导出需要各自的错误路径；若场景要求审计记录持久化后才能执行副作用，则应在执行前建立这个门槛，而不是事后误用通用重试。

## 做一次故障注入

给 mock 适配层准备可控行为：抛出暂时网络错误、返回损坏 JSON、返回正确的资料不足、返回格式正确但版本错误的答案。用同一个页面或响应封套观察它们，预期至少得到四种不同的诊断路径。

验收不以“所有请求都返回 200”为目标，而是检查：能否说明失败发生在哪层；用户能否据此选择下一步；不可重试的题目是否停止；业务错误是否进入评测失败样本；响应和日志是否没有隐藏资料或凭证。可运行测试使用合成故障，只证明分支行为，不证明真实网络故障分布。
