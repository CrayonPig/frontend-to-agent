# 19 RAG 评测：没找到，还是找到了却答错

Q03 又答成了 `pending`。如果只保留最终答案，很容易把下一步定为“加强提示词”。但可能的原因至少有三种：索引根本没有 C-B14，检索找到了却被截断，或者正确材料进入输入后生成器仍混用了版本。它们需要完全不同的修复。

第 07 篇建立任务基线，这里把同一个结果沿知识链路拆开。目标不是做出一个复杂总分，而是让一次失败能归到可行动的层，同时保留端到端任务是否完成的判断。

## 先给题目标需要什么证据

评测集除了问题与期望类别，还要标出适用证据。Q03 需要 C-B14，Q04 需要 C-B14 与 C-B20；Q14 需要冲突卡 C-T20-A、C-T20-B，不能使用普通 C-T20 替代。Q05 可以找到 C-T20，但它只证明资料未说明相关能力，不构成“支持虚拟滚动”的证据。

这样的标注仍然是教学数据中的人工标准，不是自动从参考答案里抽关键词得到的真理。若未来一个事实在多份同等有效来源出现，可标为可替代证据组，避免错误惩罚有效检索。若题目本身含糊，先修正题目并更新版本，而不是让指标替作者做决定。

对 Q08，不应给检索器一个“期待召回 T-B20”的目标。它期待的是授权层拒绝及无泄露；对 Q06，期待的是目标版本无适用资料。正负样例必须使用不同判定，不然系统越权召回得越全，分数反而越高。

## 四层检查，而不是一个平均分

可以从下面四层检查一次任务：

| 层 | 问题 | Q03 的失败例 |
| --- | --- | --- |
| 摄取 | 所需来源和修订是否在有效索引中 | C-B14 被错误标为删除 |
| 召回与排序 | 需要的证据是否进入最终候选 | 只取到 2.0，或 C-B14 被挤出 top-k |
| 输入与生成 | 选中的证据是否进入输入，断言是否受支持 | C-B14 已输入，答案仍说 pending |
| 任务 | 版本、事实、拒答、权限和输出是否满足要求 | 参数错、越权或虚构执行成功 |

召回可以用 Recall@k：在有明确应找证据的题目上，前 k 个候选覆盖了多少所需证据。比如 Q04 所需两份来源，只找到一份，覆盖比例为 1/2。对于只要求一个正确结果的任务，也可以记录首个正确结果的排名；但不把这种指标套到要求同时发现冲突双方的 Q14。

排名质量需要结合用户目标。Q14 的两张卡都保留下来，比只把一张放到第一位更有价值。Q05 的“未知”若被正确保留，也是任务通过；不能为了提高 answered 比例而鼓励胡编。越权和虚构写入可单独设为阻断项，不允许被其他题的高分平均掉。

## 一条可解释的合成失败报告

下面是设计用的记录示例，不是实际模型结果，也没有填造耗时：

```json
{
  "runId": "rag-debug-q03-example",
  "caseId": "Q03",
  "fixtureVersion": "atlas-fixture-01",
  "requiredSources": ["C-B14"],
  "retrievedSources": ["C-B14"],
  "selectedSources": ["C-B14"],
  "promptSources": ["C-B14"],
  "answerSources": ["C-B14"],
  "candidateAnswer": "1.4 使用 pending 显示等待。",
  "checks": {
    "retrievalCoverage": "pass",
    "versionScope": "pass",
    "supportedClaims": "fail",
    "taskSuccess": "fail"
  },
  "stageDurationMs": null
}
```

这个例子中连引用 ID 都是正确的，事实却错误，因此失败位于生成/答案约束层，继续扩大召回没有直接理由。反过来，如果 `promptSources` 为空，就应先检查输入装配是否因预算裁剪掉了资料，而不是宣称模型不遵循证据。

这些记录应关联到同一 trace 的阶段 observation：摄取通常属于异步更新链路，可以通过索引代次与文档修订关联；当前请求里的检索、候选选择和生成则保留父子关系。不要为了让图形好看，把几天前的摄取过程伪装成当前请求的子调用。

## 比较方案时固定分母

比较关键词、混合与重排方案时，固定题目集合、资料快照、授权策略、目标版本和生成配置。先只换检索层，观察证据覆盖与排序；再在同一生成器下观察任务变化。若同时换模型、提示词和切分方式，即使总分变好，也很难知道哪项有效。

报告至少列出每题结果、失败层、关键证据 ID、实际耗时与未测项目。耗时从单调时钟测量阶段起止，异步并行阶段的耗时不能简单相加当作端到端时间。真实模型重复运行时，要保存每次尝试，而不是挑最好的一次；离线确定性 mock 重复一致，则只能证明该 mock 的可重复性。

开发题可以帮助调整规则，独立检查题用于发现过拟合。只有 14 题的小集合不能估计所有线上问题的成功率，也不应凭一题改写就声称泛化。可以逐步加入新措辞、相似组件、版本缺失和已知错误回归，但新增题必须有明确资料与标准。

## 从仓库基线读取真实记录

在仓库根目录执行 `node examples/atlas/evaluate.mjs`，会生成 `examples/atlas/reports/baseline.json`。每题包含候选答案、格式结果、有限规则评分、检索信息和 trace；实际调用的适配器标为 `atlas-rule-mock-1`。它不会连接模型，也不会产生模型费用。

阅读报告时先看单题的 `retrieval`，再看 `candidateAnswer` 和评分，不只看汇总通过数。权限拒绝发生在检索之前的请求，不应该伪造一段检索候选或耗时来填满报表。来源修订必须来自本次实际文档对象，不能统一写死为 r1 后宣称可追溯。

仓库目前没有真实重排阶段，因此也没有重排质量和远端生成耗时。要形成完整外部 RAG 报告，需要接入后补齐这些记录，并保持缺失值为未知。独立检查划分虽与开发题分开，但资料与规则公开可读，不是盲测基准；不能从合成题全部通过推导生产准确率。

## 从一次故障得到下一条回归

练习时注入四种故障：从索引移除 C-B14；保留索引却把候选上限设得过小；候选正常却在输入装配丢掉“不阻止点击”；最后让 mock 返回错误参数。分别记录哪一层首先不满足预期。这个定位练习比给最终答案打一个 0 更能指导修复。

本教程的离线 mock 可以验证夹具选择、授权、结果契约与已知断言，不能替代真实检索模型和生成模型的质量评测。接入真实服务以后，用同一题目与记录结构补齐外部层，不覆盖原始基线。验收是每个注入错误都能定位到合理阶段，且修复后原本通过的越权、未知和冲突题仍通过。
