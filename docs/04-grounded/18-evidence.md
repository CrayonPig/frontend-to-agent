# 18 带引用的答案，真的有依据吗

助手回答 Q03：“Atlas UI 1.4 设置 `pending` 即可等待并禁用按钮，参考 C-B20。”引用存在、链接可点、资料也真实存在，但这仍然是错误答案。问题要求 1.4，引用属于 2.0；而 C-B20 也没有说等待状态自动禁止点击。

因此，引用检查至少包含两件事：来源适不适用，来源支不支持这个结论。第一件可以较多地用元数据检查；第二件涉及语义，仍要用明确的判断规则和人工复核。不能因为加上链接，就把生成结果升级为可靠知识。

## 把结论和依据连到一起

比“答案最后附一串链接”更容易核对的方式，是把关键断言对应到片段。下面是 Q03 的示意中间表示，不是要求界面展示 JSON，也不是另一个模型 SDK：

```json
{
  "claims": [
    {
      "text": "Atlas UI 1.4 使用 loading 显示等待图标。",
      "sourceIds": ["C-B14"],
      "revision": "r1"
    },
    {
      "text": "阻止组件触发 click 还需设置 disabled。",
      "sourceIds": ["C-B14"],
      "revision": "r1"
    }
  ]
}
```

检查者可以逐项询问：目标版本是否一致，来源是否属于允许上下文，原文是否包含该行为，有没有遗漏限制。两个断言都由 C-B14 支持；但“后端保证不重复提交”不在资料里，即使前两句正确，也不能顺手加上。

引用 ID 应由系统解析到已授权来源，不能让模型返回任意外链并由前端无条件渲染。展示层还要处理失效引用、文本转义和访问控制。引用点击需要重新校验当前权限；用户作答时有权访问，不代表一周后仍可读取同一份文档。

## 三种“答不全”不能混为一谈

Q05 的 C-T20 没写虚拟滚动和数据量上限，这是证据不足。正确表达是“现有资料无法确认”，而不是“肯定不支持”。后者把缺少证明误当成了否定证明。

Q14 使用两张同范围、同权威等级的冲突卡，分别说 `rowKey` 必填和可选。这里不是缺少文本，而是文本不一致。回答应指出冲突并请求维护者核实，暂不确定必填性。按检索分数挑一个胜者会掩盖实际问题；按文件名 A、B 排序也没有业务依据。

Q12 则只有部分问题得到覆盖：`precision` 默认值是 coarse，有依据；fine 是否保证误差一米内，没有依据。可以分别说清这两部分，整体标为 `insufficient_evidence`，不要为了统一结果类别而把已知默认值也删掉。

| 情况 | 系统拥有的证据 | 应给用户的下一步 |
| --- | --- | --- |
| 资料不足 | 没有覆盖关键断言 | 补充目标资料或说明未知 |
| 资料冲突 | 同范围结论彼此不兼容 | 核实来源优先级或修正文档 |
| 部分覆盖 | 一些断言可确认，另一些不可确认 | 分别说明已知与缺口 |

结果类别要帮助用户继续，而不是把所有不完整回答都包装成“系统繁忙”。版本未给定的 Q07 又是另一类：先问目标版本，不必立即进入生成。

## 校验器可以挡住什么

服务端能确定性检查引用 ID 是否属于允许集合、修订是否匹配、目标版本是否满足、字段结构是否合约。还可以对本教程固定参数事实建立规则断言，例如 Q03 不得把 `pending` 当 1.4 用法。这样能捕获已知失败，但不能证明开放问题的全部自然语言都准确。

因此不要命名一个 `validateResult` 就声称实现了通用事实核查。它的覆盖范围应写明：结构校验、引用范围校验和已知业务规则。人工评价与可选模型评价可以补充语义判断，但评价器自身也要有版本、样例和误判检查。让生成模型自己说“引用支持全部结论”，只是又生成了一段需要验证的文本。

对无权访问问题，权限错误应在资料进入模型前解决。拒绝理由使用通用范围说明，不引用隐藏文档名称、版本或正文。作者能在测试夹具里看到 T-B20，并不意味着助手可以拿它来解释为什么拒绝。

## 在离线实现里看清验证的上限

`examples/atlas/core.mjs` 的 `validateResult` 检查六种结果类别、对应文本字段，以及回答或冲突结果中的引用是否属于允许资料；不可信注入卡不能充当引用。它要求调用方传入已经授权的资料集合，不能传全部测试夹具再期待函数自动猜出用户身份。

一个结构合法的“1.4 使用 pending”仍可能通过通用结构与引用检查。因此 `examples/atlas/expectations.mjs` 另外保存已知任务断言，测试中也保留了“流畅但错版本”的反例。这种分工比让一个函数名包办所有可信性更诚实：输入输出有契约，有限题集有断言，开放自然语言还需要真实模型评测和人工复核。

读者可以故意保持 sourceIds 为 C-B14，只修改候选答案里的参数，观察结构检查和任务判定出现不同结果。这个小实验的收获是区分校验层，而不是证明关键词规则能判断所有语义等价句。

## 把实际证据放进运行记录

一条回答链路至少关联请求的目标版本、索引代次、实际选中的文档与修订、最终引用集合和结果类别。检索候选不等于最终使用证据：候选可能被截断，生成器也可能忽略一段。报告应区分“召回过”“进入输入”和“在答案中引用”，否则无法定位丢失发生在哪里。

这里记录的是外部输入输出与业务动作，不是模型私密推理。合成测试可以保存完整候选答案；真实数据按用途最小化、脱敏、限权并设置保留期限。若日志查看者无权看原文，仅记录受控引用或摘要也需要考虑是否暴露文档存在性。

实践时用相同的 C-B14 分别评三份答案：正确区分 loading 与 disabled；误写 pending；正确参数后附加后端幂等保证。前一份通过，后两份分别在版本事实和无依据扩展上失败。再加入 Q05、Q12、Q14，确认未知、部分覆盖和冲突各有可理解的反馈。

验收不是引用数量达到某个阈值，而是每条关键结论都能找到适用依据，未覆盖内容不被硬补，冲突不被排序掩盖。下一篇把这些判断拆到 RAG 的不同步骤，避免每次答错都只改提示词。
