# 20 文档更新以后，旧知识怎么退出系统

助手第一次导入文档后，Q03 能正确回答，并不意味着系统以后一直正确。资料会修订、删除，权限也会变化。更棘手的情况是：新内容已入库，旧索引和旧答案缓存仍在服务；或者删除事件已经处理，迟到的旧导入任务又把文档写回来了。

这一篇把知识当成有生命周期的数据。示例更新都是独立测试事件，不改变 `atlas-fixture-01` 的原始事实：C-B14 仍描述 1.4，C-B20 仍描述 2.0，C-T20 的虚拟滚动能力仍未知。

## 产品版本、内容修订、索引代次各管一件事

同一个产品版本的文档可能修正错字、补充限制，这属于内容修订；产品升级可能同时保留旧版资料；切分器或 embedding 模型变化，则可能要求重建派生索引。把它们都叫 version，会让缓存和查询失去明确含义。

建议分别记录 `productVersion`、`revision` 与 `indexGeneration`。一个请求可以要求产品 1.4，读取 C-B14 的 r1，并从某个索引代次召回。后续如果文档 r2 改了说明，目标产品仍是 1.4，但旧答案可能失效。

索引是派生物，权威来源和处理事件应可追溯。每次更新以稳定文档 ID 找到旧单元集合，写入新集合并移除不再存在的片段，不能仅追加新片段。否则旧参数限制会长期混在候选里，生成器看到的“冲突”其实是更新程序制造的。

## 删除是一条必须记住的状态

考虑一个独立的合成时序：序号 10 导入一份测试卡，序号 11 修改它，序号 12 删除它，随后队列重试了序号 10。如果程序只按事件到达顺序覆盖，资料会复活。

下面的 TypeScript 是状态转换示意，`sequence` 来自可信来源的单调顺序，不是任意客户端时钟；片段写入与水位更新在真实系统中需要原子化或可恢复设计：

```ts
type Event = {
  documentId: string
  sequence: number
  kind: 'upsert' | 'delete'
  body?: string
}
function shouldApply(event: Event, watermark: number) {
  return event.sequence > watermark
}
```

删除后仍保留删除水位或墓碑（tombstone），用来拒绝旧事件。墓碑不是要永久保存全文，它保存的是阻止旧状态恢复所需的标识与顺序。若来源没有可靠序号，就要使用来源修订、条件写入或重新拉取权威状态；不能拿本机时间戳比较就声称解决了乱序。

幂等处理要求相同事件重放不增加重复单元。对同一文档的新事件，又要检查它是否真的较新。两者不同：幂等防重复，顺序控制防回退。测试应该同时包含重复写入、乱序更新、删除后迟到重放，以及中途失败后恢复。

## 重建索引，不让用户看到半成品

解析器或表示模型变化时，可以建立新的索引代次，导入固定来源快照，运行题集与隔离检查，再切换读入口。失败则继续读取旧代次，但要明确哪些更新尚未纳入，不能无限期用旧数据冒充当前。

Elasticsearch 8.19 的 aliases API 可以在一次请求中执行多项别名操作。以下为未在外部实例执行的示意，前提是两个索引已建立且新索引完成校验：

```http
POST /_aliases
Content-Type: application/json

{
  "actions": [
    { "remove": { "index": "atlas-units-g1", "alias": "atlas-read", "must_exist": true } },
    { "add": { "index": "atlas-units-g2", "alias": "atlas-read" } }
  ]
}
```

这解决的是入口切换，不自动解决数据一致性。构建 g2 时发生的新更新需要补齐到切换水位；删除与撤权也必须同步到所有可能读取的路径。响应不确定时先查询实际别名状态再决定重试，不要因客户端超时就假定切换没发生。[官方 aliases API，核对于 2026-10-26](https://www.elastic.co/guide/en/elasticsearch/reference/8.19/indices-aliases.html)

回滚到 g1 也不是永远安全。如果 g1 包含后来删除的资料或过期权限，直接切回会重新暴露旧内容。回滚前必须应用当前删除与授权约束；必要时只能回滚程序，不能回滚数据可见性。

## 缓存也属于知识退出路径

索引更新了，答案缓存不变，用户仍会看到旧结论。答案应携带其依赖的来源修订或索引代次，缓存键和命中校验覆盖身份范围、权限版本、目标版本及数据版本。某个来源删除后，要让相关答案失效；无法精准追踪依赖时，可以牺牲命中率，提升全局知识代次。

权限撤销比普通内容修订更敏感。即使缓存 TTL 还没到，也不能继续返回已无权访问的答案。服务端在命中路径仍需核对当前授权；过期不是唯一的失效条件。这里先建立规则，具体缓存分层放到第 37 篇。

观测上记录事件 ID、来源序号、旧新修订、索引代次、处理结果和耗时。删除失败不能只写成一条普通 warning 后继续宣称同步成功。对运维者暴露的日志同样受权限约束，不用复制原文来证明删除发生过。

## 离线状态机与真实存储的差距

本仓库的 `DocumentStore.apply` 用递增修订拒绝旧更新，并保留删除记录；每次有效变更提升 generation，缓存据此失效。测试覆盖了重复更新、删除后的旧事件重放，以及新事实导致答案变化。它使用内存 Map，进程退出后不会保存知识更新状态，不能被描述为可靠的分布式摄取系统。

这里将修订数作为合成来源的单调顺序，是夹具的明确约定。现实来源若允许回填、分支或并行编辑，修订字符串未必可直接比较；需要来源自己的冲突策略或事件序号。即使应用算对了先后，数据库提交失败也可能造成水位和索引不一致，因此还需要持久化事务、可重放队列或分阶段提交记录。

从内存实现升级时先保留相同时间序列测试，再增加重启恢复和写入中断场景。不要换了数据库就移除旧事件回放测试，因为最危险的回退往往发生在重试与恢复路径。

## 用时间顺序验收，而不是只查一次

为独立的更新测试创建一份合成临时文档，依次执行：导入、重复导入、更新、删除、重放旧导入。每一步检查有效单元数、查询结果和缓存可用性；最后应该看不到该文档，也不能从旧缓存读到它。原始 14 题资料另行重置，避免测试污染基线。

再模拟新代次构建中断：读入口应保持已验证代次，失败批次能重试但不产生重复；切换后抽查 Q03、Q06、Q08、Q14，确保内容、缺失版本、权限和冲突语义没有变化。验收产出是一份事件与可见状态的对照记录。系统能解释“这份旧知识为什么已退出”，才算从一次导入演示走向持续维护。
