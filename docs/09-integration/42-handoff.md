# 42 如何证明这个知识助手可以交给别人使用

交付时最有价值的问题不是“能不能演示一下”，而是“换一个没参与开发的人，能不能从干净目录重现同样的判断”。开发者知道哪些参数要填、哪些问题暂时别问，这些隐含知识会让一次演示看起来比实际系统可靠。

这篇把 Atlas 助手交给另一位读者。交付对象是完整教程与一个本地合成教学程序：能检查任务结果、授权、更新、工具预算和沙箱恢复；不是接入真实模型、账号系统和生产数据库的在线产品。文档站发布只代表文章可以访问，不代表模型后端已经部署。

## 从空环境开始，而不是从作者的终端开始

仓库文档要求 Node.js 22+ 与 npm。完整合成程序使用 `.mjs` 和 Node 内置测试，无需真实模型密钥、数据库或额外运行依赖。先获取仓库，在根目录执行：

```bash
npm ci
node scripts/check-docs.mjs
npm test
node examples/atlas/evaluate.mjs
npm run docs:build
```

这些命令承担不同责任。`npm ci` 根据已有锁文件安装文档站依赖；文档检查验证 42 篇编号、主标题与本地链接；测试运行器检查隔离、更新、预算等程序行为；评测命令保存合成题的候选输出与规则判断；构建检查 VitePress 的页面和站内链接。不能因为最后一条构建成功，就把前面的业务验证省掉。

本轮实际命令和环境记录在[实施与验证记录](../reviews/progress.md)，逐篇范围在[覆盖矩阵](../reviews/coverage.md)。如果命令失败，应保留输出与失败步骤，而不是把报告里的“通过”复制成自己的结果。依赖下载受限、Node 版本不匹配和测试断言失败也是不同问题；诊断它们不需要关闭死链检查或修改业务预期。

启动本地合成服务另开终端：

```bash
node examples/atlas/server.mjs
```

然后打开 `http://127.0.0.1:8787`。该入口绑定回环地址，固定使用合成主体，不提供真实登录。以下请求使用服务的实际字段 `question` 和 `version`，不是正文设计示意里的可选别名：

```bash
curl -N http://127.0.0.1:8787/api/ask \
  -H 'Content-Type: application/json' \
  -d '{"question":"Atlas UI 2.0 要按列展示记录，用哪个组件？","version":"2.0"}'
```

预期收到逐行 JSON 事件：`started`、若干 `delta` 和 `completed`。这只是完整合成结果的分块传送，不是供应商的 token 流。页面的停止按钮终止本地等待；不能据此推断一个未来接入的远端请求没有执行。示例的实际协议、限制和完整源码入口见 [examples/atlas/README.md](https://github.com/CrayonPig/frontend-to-agent/blob/main/examples/atlas/README.md)。

## 先复核事实，再看通过率

评测程序把 Q01–Q14 的题目与预期分开保存，并将候选答案写入 `examples/atlas/reports/baseline.json`。报告可以回答“哪一份输出被哪个规则判定”，而不是只留下一个总分。运行 ID、资料版本和适配器版本一起保留，便于修改后比较。

本地规则 mock 专门识别教学意图。它通过这 14 题，证明固定资料、结果契约与测试管道可以协同工作；不证明它理解任意自然语言，更不证明真实模型在相同题目上的质量。检查集与开发集分开，仍公开在同一仓库，不能当作未被开发者看过的盲测集。接入模型后应另外准备独立题目，必要时多次运行，并报告波动、失败与人工分歧。

交接者可以先抽查四条：

| 检查 | 应看到的行为 | 如果不符合，应查哪里 |
| --- | --- | --- |
| Q03：1.4 按钮 | loading 与 disabled 分工，引用 C-B14 | 版本过滤、候选答案和事实断言 |
| Q05：百万行虚拟滚动 | 保留未知，不能断言支持或不支持 | 生成约束与未知判定 |
| Q08：另一租户资料 | 拒绝，且无隐藏文档元数据 | 入口授权、候选、引用与日志 |
| Q14：同版本冲突 | 说明冲突，不任选一个结论 | 本题专用资料替换与来源优先级 |

再故意把 Q03 答案替换成“pending 自动禁用”。格式可以合法，任务判定仍必须失败。如果错误答案没有被检测到，先修复评测，而不是宣布系统可靠。规则检查也只覆盖预先定义的断言；真实回答中的遗漏、误导和隐含承诺还需要人工审阅。

## 一次交付要带三种失败证据

第一种是边界拒绝。越权主体、额外工具参数、过期确认、不同内容复用幂等键都应失败。这里的“失败”是执行器成功守住规则，不应在产品统计里和网络故障混为一谈。

第二种是不确定结果。让调用超过本地等待预算，再观察远端替身仍然执行；让沙箱草稿保存之后、响应之前中断，恢复时用已保存回执核对，而不是重复创建。测试报告必须说明检查点保存在哪、何时落盘。本示例的文件替换与内存事务只说明单进程语义，不提供真实数据库的跨进程事务保证；如果进程在保存快照之前退出，最后一次内存变更可能丢失。

第三种是内容失败。候选资料正确，答案仍可能使用错误参数；引用存在，却不支持断言；改了 Prompt 之后，正常题通过但拒答题泄漏了隐藏信息。这些失败需要保留候选、规则版本和来源，不要求记录模型私密推理。合成资料可以保存全文；真实任务需要最小化、脱敏、访问控制和保留期限。

交付时不要只放成功截图。至少能向接手者展示一份主动拒绝的结果、一份受控中断的恢复记录，以及一份被评测拦下的流畅错误答案。它们说明系统如何承认限制，也给下一次修改提供回归条件。

## 接入外部能力时，验收需要重新开始

第 11 篇的 Langfuse、第 15 篇的 Elasticsearch、第 34 篇的 MCP 都有明确的协议或版本边界。当前默认程序不连接这些服务。真实模型的调用、真实用量和费用同样未由 mock 验证。不能把库安装成功、HTTP 成功或 trace 出现当作完整业务验收。

| 可选接入 | 还需要新增的验证 |
| --- | --- |
| 真实模型适配器 | 凭证只在服务端；格式、拒答、截断与用量映射；同题多次评测 |
| Elasticsearch | 实际版本、映射与过滤；同租户/跨租户检索；删除与切换快照 |
| Langfuse | 首条链路可见；父子关系；导出前脱敏；flush/shutdown；查看和删除权限 |
| MCP 工具服务 | 协议版本与能力发现；会话和授权边界；业务参数与结果校验 |
| 持久化存储 | 原子性、并发、崩溃窗口、回执查询、备份恢复与撤权后的继续执行 |

这些验证应在明确授权的环境里进行。本教程不要求创建第三方账号、购买服务或操作真实公司系统。没有条件接入时，状态写“未验证”，比用模拟成绩替代更有价值。

成本也采用同样口径：合成调用没有真实 token 用量或供应商账单，缺失值记为未知，不是零。延迟测试若使用本机调度和人为延迟，只能解释机制，不能作为线上 p95。接手者能分清数据来源，比看到一个漂亮但无依据的数字更重要。

## 发布与回滚应交代到什么程度

发布记录至少固定程序、资料包、索引、Prompt、模型适配器、工具与 Skill 的版本，附上评测记录及已知限制。变更某一项就检查相关回归，而不是只看前端页面是否打开。若准备接入真实系统，再约定符合业务风险的通过门槛、小流量范围和人工接管条件；不照搬教程题集的分数作为生产门槛。

回滚也要说明对象。退回 Prompt 标签不能恢复被删除的文档，退回前端代码不能撤销已经保存的草稿。对于只读回答，可以回到上一份经过验证的配置与资料快照；对于状态变更，先核对回执与当前资源，再按业务规则决定后续动作。不能把“重新部署旧包”写成万能恢复策略。

静态文档站沿仓库现有 GitHub Pages 工作流发布。这个工作流与合成助手服务是两件事：文章发布成功，不会自动把 `server.mjs` 变成公网服务。示例保持本地运行，部署设置不因教程写作而改变。

## 接手者最后应能回答的问题

请另一位读者按命令启动，选择 Q03、Q08、Q14，解释每个结果的依据；再运行故障测试，找出一条取消后仍执行、一条确认失效、一条删除阻止旧数据恢复的证据。最后要求他指出三项尚未验证的外部能力，并说明接入后需要补什么测试。

如果读者只能复述“用了 RAG 和 Agent”，交付还不完整。如果他能从题目追到资料、候选、结果、回执与版本，并知道哪些信息不应进入模型或日志，那么这个教学助手已经具备可复现的交接材料。后续是否接入模型、增加工具或保留固定流程，可以在同一套证据标准下决定。
