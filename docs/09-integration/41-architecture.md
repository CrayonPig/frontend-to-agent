# 41 一次问题经过了哪些模块

现在重新看最初那句“项目还在 Atlas UI 1.4，提交中用哪个参数”，答案仍然不长：`loading` 显示等待，`disabled` 阻止组件发出 click。系统却多了授权、检索、证据检查、任务记录与版本管理。它们并不是为了让这句话显得复杂，而是为了在资料更新、请求取消、权限变化或工具超时时，仍然知道这句话为什么成立。

本篇把贯穿案例按两条流重新连接：用户问题怎样得到处理，文档变化怎样影响下一次回答。图中区分仓库的合成实现与可选外部能力，不把教程讲到过的组件都画成已部署服务。读完后，应能从一次错误答案反向找到负责它的边界，而不只是背下模块名称。

## 两条可运行路径，各自证明什么

[本地示例](https://github.com/CrayonPig/frontend-to-agent/tree/main/examples/atlas)采用一个 Node 进程和合成数据。网页只贯通只读问答；其他模块通过函数调用与测试独立演练，不把全部能力接入同一个聊天入口。它足以检查契约、过滤与执行控制，不需要把每个方框拆成服务。

```text
默认 HTTP 页面路径
浏览器 → 应用入口（固定合成身份、请求校验、requestId）
             → 授权范围 → 关键词检索 → 规则 mock → 结果与引用
             → 分块输出；本地 Trace 摘要

可独立调用、由测试验证的教学模块（未全部接入 HTTP 页面）
请求治理：重试预算、超时、并发
执行控制：固定工作流 / 受限循环 → 只读构建状态
沙箱草稿：独立调用者 → 预览 → 明确确认 → 幂等写入与回执
恢复：业务检查点文件；与 trace 分开
治理：缓存、上下文、记忆、Prompt 标签、成本与分位数计算

独立 TypeScript 观测集成路径：examples/atlas-observability
固定 A30：CLI → 授权 → 合成资料读取/选择 → 只读构建工具
             → Prompt 获取与装配 → HTTP 模型替身 → 结果校验/评分
受限循环：CLI → 脚本选择器 / 显式 HTTP 选择器 → 执行端校验动作与预算
             → 合成资料或只读构建工具 → 回填结果 → 再选择/停止
两条路径 → 真实 Langfuse/OpenTelemetry SDK → 本地 OTLP 接收端

可选真实外部服务：真实模型、Elasticsearch、Langfuse 平台、MCP
                 不属于默认已连接或已验证的运行路径
```

第二条路径包含固定 A30“查询 virtual 参数并核对构建状态”工作流，以及独立的 TypeScript 受限循环；它们运行真实 SDK 和序列化导出，但默认的模型、Prompt 服务与 OTLP 接收端仍在本地。它不是 Q01–Q14 的全部模型版实现。这里的“真实”修饰的是 SDK 行为，不代表真实模型质量或第三方平台送达已经验证。它比内存 trace 多检查了生命周期、HTTP 边界、实际版本关联和导出内容；它也没有把所有可选模块接入同一个产品入口。

模型 mock 不是一个能力较弱的真实模型，而是受控替身。它让同一输入产生可检查的合成行为，能证明“无权资料没有进入上下文”，不能证明开放问题上的自然语言理解能力。内存状态同样能演示检查点语义，但不能自动提供进程崩溃后的持久性、跨实例一致性或备份恢复。具体运行边界以[交付验收](42-handoff.md)和示例 README 为准。

已有前端经验在这里仍有帮助。页面组件与服务模块都适合按职责拆分；区别在于，一个答案依赖的事实和授权不能被 UI 封装隐藏掉。把请求包装进 `useAssistant()` 并不会让调用具有新的可信度，关键判断仍要在执行端完成。

## 沿 Q03 走一遍请求流

Q03 指定 Atlas UI 1.4。入口首先检查问题与版本格式，并使用服务端确定的 `reader-a`、`demo-aurora` 身份。示例采用固定合成身份是为了本地复现，真实接入必须替换为经过验证的会话。接受一个客户端提交的 `tenantId` 并把它一路传下去，不等于完成身份确认。

检索范围由产品、目标版本、租户、权限和有效资料共同决定。C-B20 虽然名称相似，但属于 2.0，不应替代 C-B14；T-B20 即使包含相关单词，也因权限不符而不能进入候选。过滤在送入模型之前发生，模型不负责从秘密堆里挑出“可以说”的部分。

基础 HTTP 示例里的规则 mock 直接读取过滤后的结构化事实，`assembleContext` 独立演示材料预算。TypeScript 集成示例则将当前问题、允许资料和回答约束装配成实际 HTTP 请求，并记录使用的 Prompt 对象与配置。默认接收请求的仍是本地模型替身，所以已经验证的是请求装配与传输路径，不是某个商业模型的回答质量。候选答案返回后，结构检查确认结果类别与字段合法，引用检查确认来源确实在允许范围内，再检查关键结论是否受到资料支持。对合成样例可以用明确断言完成一部分事实检查；对真实开放回答，仍需任务评测和人工抽样，不把规则覆盖之外的结论自动判为正确。

上述结构/事实校验由独立函数与回归测试共同检查；默认 HTTP 路径不含独立模型事实审查器。最后，浏览器只接受当前请求的结果。若用户已经发起新问题，旧请求即使后来成功，也不能覆盖新界面。观测记录保存这次执行的版本、候选标识、终态与必要耗时，帮助后续解释失败；它不承担授权决策，也不是事实来源。

把这条路径看成几个互不相同的关口，会更容易排错：

| 看到的现象 | 应先检查的证据 | 不能直接推出的结论 |
| --- | --- | --- |
| 候选里没有 C-B14 | 快照版本、过滤条件、检索结果 | 模型“不懂按钮” |
| 候选正确却使用 pending | 候选答案、Prompt 版本、结论检查 | 增加向量维度就会解决 |
| 服务端正确、页面出现旧答案 | requestId 与 UI 状态转换 | 知识索引有问题 |
| 取消后仍有调用记录 | 请求预算、执行回执 | 取消按钮没有任何作用 |

## 固定工作流的观测树怎样对应调用链

独立包的 A30 用根 `assistant.task` 包住一次逻辑执行，下面依次产生 `authorize`、`retrieve.docs`、`select.evidence`、`tool.build_status`、`prompt.resolve`、`model.answer` 和 `answer.validate`。其中只有 `model.answer` 声明为 generation；其他步骤记录各自的输入或结果摘要。`retrieve.docs` 目前是确定性读取合成卡，既不是 Elasticsearch，也不包含 rerank。

这棵树由真实 SDK 的异步上下文建立。CLI 刷新导出缓冲，随后关闭 SDK；本地 OTLP 接收端把实际收到的序列化包存入 `reports/<command>-otlp.json`，同名 `-spans.json` 是便于核对的派生视图；通用 `otlp.json`、`spans.json` 仅保留最近一次执行。任务报告保存 `traceId`、`runId`、`taskId`、尝试号与版本，分数保存在 `quality` 和校验 observation 中。不要把这些本地质量记录称作已经创建了平台 Score 对象。

Prompt v1/v2 的比较会产生独立 traces，通过共同任务与题目标识关联。失败记录的复盘首先对已存候选输出重新评分，不产生模型调用；随后以固定 v2 发起一个新尝试，产生新的执行链路。这不是把旧 trace 当程序执行，也不是重放模型私密推理。生产环境的真实恢复仍应依赖业务检查点与外部回执。

还应对照记录检查没发生的步骤。注入越权材料时，`select.evidence` 拒绝并提前结束，不应继续出现模型调用。Prompt fallback 则明确标记本地来源和本地版本，不能伪装成平台版本。让架构图表达这些分支，比要求每条 trace 都有相同数量的方框更有价值。

## SDK 受限循环不是给固定步骤换名字

固定 A30 由应用直接决定先读卡、再查构建、最后回答，步骤不会因为模型生成一段文字而改变。新增 TypeScript 循环提供两种选择器：默认脚本用于确定性演练，显式加 `--http-selector` 后，“下一步选择”才变成实际 HTTP 请求。选择器根据当前状态提出动作，执行器校验动作是否属于允许集合、参数是否合约、任务预算是否足够，执行后把结果放回状态，再进入下一次选择或停止。两者要分开测，不能因为都有 generation 就统称为 Agent。

默认脚本选择器与本地 HTTP 替身都只能验证循环驱动、动作拒绝、预算和链路关系，不代表真实模型选择更好。代码可以显式连接外部 HTTP 选择器，但本次没有运行该模式；是否支持目标服务的协议、选择质量和费用，仍需额外验证。

当前允许动作只有 `read_docs`、`build_status` 和 `finish`。前两者分别读取当前范围合成证据、获取只读构建状态；最后一个携带候选答案，但只有证据齐全且独立质量检查通过才算完成。选择器不能通过动作 JSON 扩大预算、切换主体或增加写工具。

循环的根节点是 `agent.task`，每次尝试产生 `agent.step`，其下包含 `agent.choose` 和实际执行的工具或 `answer.validate`。HTTP 模式的 `agent.choose` 才标为 generation；脚本模式是普通 span，不伪造模型调用。循环之外的 `task.stop` 保存停止原因、步数与工具次数。报告里的 `syntheticCostUnits` 是预先约定的教学预算，`cost` 和 `usage` 仍为未知，不能换算成账单。

这里的选择指令来自 `agent.ts`，不是固定工作流的 `atlas-answer` 平台 Prompt 对象。A30 的 Prompt v1/v2 治理与循环选择策略是两个独立变化来源；报告要分别读，不能因为一个包里有 Prompt 管理就假定所有 generation 都已经关联平台版本。

新 TypeScript 循环的运行记录也不应与旧 JavaScript 示例的恢复能力拼接成一个不存在的系统。`examples/atlas` 的文件检查点、沙箱回执和重启恢复测试是独立演练；新增 SDK 循环即使记录了 taskId 和每一步 observation，也不能因此声称已完成持久化恢复。需要恢复时，仍要把执行状态提交到业务存储、核对外部回执，并在新尝试中重新授权，而不是把 trace 重新播放一遍。

## 查询实时状态，多的是执行边界

文档能说明组件参数，不能证明某次演示构建现在是否完成。查询构建状态时，固定工作流先确定组件和版本，再调用只读工具。工具输入来自模型也好、代码也好，都要重新检查身份、范围、允许参数和预算；工具成功后还要核对返回的是不是请求的构建。

若任务进一步要求保存迁移草稿，就跨过了副作用边界。仓库中的草稿模块由独立调用者演练，受限 Agent 的动作集合不含写入，HTTP 页面也不会自动保存。保存前先生成预览，确认记录绑定主体、任务、内容与版本；执行时核对确认仍然有效，使用幂等键与动作指纹避免重复写入。超时之后先查询已知操作的回执，而不是重新生成一段内容并沿用旧确认。

这里最容易混淆的是三个“存下来”：

| 保存内容 | 目的 | 恢复时的用途 |
| --- | --- | --- |
| 会话历史或摘要 | 延续用户上下文 | 帮助理解当前问题，仍可能过期 |
| 业务任务检查点与执行回执 | 确认做到哪一步、什么已发生 | 决定是否继续、是否需要重新确认 |
| trace 与步骤记录 | 调试、审计和质量归因 | 查执行证据，不代替真实状态核对 |

一次恢复可以产生新的 trace，却仍属于同一 task。它不应该把几小时的任务硬塞成一条持续打开的调用链。反过来，即使完整 trace 丢失，只要业务状态与回执健全，也不应因此重复保存草稿。观测与恢复相互关联，却是两个不同的正确性问题。

## 文档更新流怎样改变答案

请求流看起来是向前走，知识变化却会影响多个下游副本。假设 C-T20 的下一份修订正式补充了虚拟滚动说明，不能只更新网页正文，然后期待所有答案自然变新。

```text
权威来源变更 / 删除
  → 校验来源修订与权限元数据
  → 构建待发布的文档单元与索引快照
  → 检查完整性、回归题与删除标记
  → 切换有效快照
  → 失效检索缓存、答案缓存及相关引用
  → 新请求使用新快照；旧运行保留当时版本证据
```

本系列没有把“新增虚拟滚动支持”写入原始 `atlas-fixture-01`。上面只是更新情景，若要实践，应建立明确的新资料包版本并修改相应题目的判定依据。否则会出现一种非常隐蔽的错误：程序已经读取了新事实，评测仍使用旧答案，或者评测期待新能力，资料里却没有任何支持。

删除与撤权比修改更严格。不能只等待缓存自然过期；即使已经生成过答案，当前请求也应重新检查权限和来源有效性。失败重建不能把带旧修订的数据重新覆盖到新版本之上。旧运行证据可以按保留政策用于审计，但不应因此重新变成用户可读的知识。

## 可选模块什么时候才值得进入图

记忆适合保存经过允许、带来源和期限的偏好，不适合代替组件权威文档；Skill 适合复用操作步骤，不等于把全部资料塞进提示词；MCP 解决协议接入与发现，不负责替应用决定授权；多 Agent 只有在可独立验收的分工收益超过协调成本时才有意义。

因此架构图里的可选模块应附带触发条件。例如“出现多个客户端重复适配同一工具”才评估 MCP，“固定并行检索仍不能满足独立审阅需求”才比较多 Agent。没有这个条件，图上的空框不算技术债，更不需要为了系列完整而实现。

真实模型与 Langfuse 平台也遵循同一规则。独立包已经提供真实 SDK 到本地接收端的集成路径，平台接入不能再只停留在概念图；但本地接收通过仍不能替第三方平台签字。真实模式必须显式配置和启用，再核对平台内可见链路、版本、父子关系、查看与删除权限。没有执行这个步骤时，状态写“平台送达未验证”，不能把教程里的预期输出复制进运行报告。

## 用一个故障检验这张图

取 Q05：AtlasTable 2.0 是否支持百万行虚拟滚动。先让候选正确包含 C-T20，再给生成结果故意填入“支持”。若系统仅因检索成功就显示任务完成，问题发生在结果检查与评测边界；此时换搜索引擎不能直接解决它。

再把同一题的权限或来源修订改变，检查答案缓存是否失效；最后停止页面等待，检查任务与 UI 是否各自留下真实状态。三次变化只改一个条件，才能知道架构中的每条责任线是否真的生效。

本篇的交付是一张与实际代码相符的架构图，以及一份能从故障现象定位到责任层的说明。下一篇将把启动、测试、未支持范围和恢复限制交给一个没参与写作的人，检查这个系统是否真的可以复现。
