# 41 一次问题经过了哪些模块

现在重新看最初那句“项目还在 Atlas UI 1.4，提交中用哪个参数”，答案仍然不长：`loading` 显示等待，`disabled` 阻止组件发出 click。系统却多了授权、检索、证据检查、任务记录与版本管理。它们并不是为了让这句话显得复杂，而是为了在资料更新、请求取消、权限变化或工具超时时，仍然知道这句话为什么成立。

本篇把贯穿案例按两条流重新连接：用户问题怎样得到处理，文档变化怎样影响下一次回答。图中区分仓库的合成实现与可选外部能力，不把教程讲到过的组件都画成已部署服务。读完后，应能从一次错误答案反向找到负责它的边界，而不只是背下模块名称。

## 先画正在运行的系统

[本地示例](https://github.com/CrayonPig/frontend-to-agent/tree/main/examples/atlas)采用一个 Node 进程和合成数据。网页只贯通只读问答；其他模块通过函数调用与测试独立演练，不把全部能力接入同一个聊天入口。它足以检查契约、过滤与执行控制，不需要把每个方框拆成服务。

```text
默认 HTTP 页面路径
浏览器 → 应用入口（固定合成身份、请求校验、requestId）
             → 授权范围 → 关键词检索 → 规则 mock → 结果与引用
             → 分块输出；本地 Trace 摘要

可独立调用、由测试验证的教学模块（未全部接入 HTTP 页面）
请求治理：重试预算、超时、并发
执行控制：固定工作流 / 受限循环 → 只读构建状态
沙箱草稿：独立调用者 → 预览 → 明确确认 → 幂等写入与回执
恢复：业务检查点文件；与 trace 分开
治理：缓存、上下文、记忆、Prompt 标签、成本与分位数计算

可选外部适配：真实模型、Elasticsearch、Langfuse、MCP
              不属于默认已连接或已验证的运行路径
```

模型 mock 不是一个能力较弱的真实模型，而是受控替身。它让同一输入产生可检查的合成行为，能证明“无权资料没有进入上下文”，不能证明开放问题上的自然语言理解能力。内存状态同样能演示检查点语义，但不能自动提供进程崩溃后的持久性、跨实例一致性或备份恢复。具体运行边界以[交付验收](42-handoff.md)和示例 README 为准。

已有前端经验在这里仍有帮助。页面组件与服务模块都适合按职责拆分；区别在于，一个答案依赖的事实和授权不能被 UI 封装隐藏掉。把请求包装进 `useAssistant()` 并不会让调用具有新的可信度，关键判断仍要在执行端完成。

## 沿 Q03 走一遍请求流

Q03 指定 Atlas UI 1.4。入口首先检查问题与版本格式，并使用服务端确定的 `reader-a`、`demo-aurora` 身份。示例采用固定合成身份是为了本地复现，真实接入必须替换为经过验证的会话。接受一个客户端提交的 `tenantId` 并把它一路传下去，不等于完成身份确认。

检索范围由产品、目标版本、租户、权限和有效资料共同决定。C-B20 虽然名称相似，但属于 2.0，不应替代 C-B14；T-B20 即使包含相关单词，也因权限不符而不能进入候选。过滤在送入模型之前发生，模型不负责从秘密堆里挑出“可以说”的部分。

在真实模型接入设计中，接下来应装配当前问题、允许资料和回答约束，交给模型适配层。本地规则 mock 直接读取过滤后的结构化事实，`assembleContext` 则独立演示材料预算，不能声称已完成真实模型上下文调用。候选答案返回后，结构检查确认结果类别与字段合法，引用检查确认来源确实在允许范围内，再检查关键结论是否受到资料支持。对合成样例可以用明确断言完成一部分事实检查；对真实开放回答，仍需任务评测和人工抽样，不把规则覆盖之外的结论自动判为正确。

上述结构/事实校验由独立函数与回归测试共同检查；默认 HTTP 路径不含独立模型事实审查器。最后，浏览器只接受当前请求的结果。若用户已经发起新问题，旧请求即使后来成功，也不能覆盖新界面。观测记录保存这次执行的版本、候选标识、终态与必要耗时，帮助后续解释失败；它不承担授权决策，也不是事实来源。

把这条路径看成几个互不相同的关口，会更容易排错：

| 看到的现象 | 应先检查的证据 | 不能直接推出的结论 |
| --- | --- | --- |
| 候选里没有 C-B14 | 快照版本、过滤条件、检索结果 | 模型“不懂按钮” |
| 候选正确却使用 pending | 候选答案、Prompt 版本、结论检查 | 增加向量维度就会解决 |
| 服务端正确、页面出现旧答案 | requestId 与 UI 状态转换 | 知识索引有问题 |
| 取消后仍有调用记录 | 请求预算、执行回执 | 取消按钮没有任何作用 |

## 查询实时状态，多的是执行边界

文档能说明组件参数，不能证明某次演示构建现在是否完成。查询构建状态时，固定工作流先确定组件和版本，再调用只读工具。工具输入来自模型也好、代码也好，都要重新检查身份、范围、允许参数和预算；工具成功后还要核对返回的是不是请求的构建。

若任务进一步要求保存迁移草稿，就跨过了副作用边界。仓库中的草稿模块由独立调用者演练，受限 Agent 的动作集合不含写入，HTTP 页面也不会自动保存。保存前先生成预览，确认记录绑定主体、任务、内容与版本；执行时核对确认仍然有效，使用幂等键与动作指纹避免重复写入。超时之后先查询已知操作的回执，而不是重新生成一段内容并沿用旧确认。

这里最容易混淆的是三个“存下来”：

| 保存内容 | 目的 | 恢复时的用途 |
| --- | --- | --- |
| 会话历史或摘要 | 延续用户上下文 | 帮助理解当前问题，仍可能过期 |
| 业务任务检查点与执行回执 | 确认做到哪一步、什么已发生 | 决定是否继续、是否需要重新确认 |
| trace 与步骤记录 | 调试、审计和质量归因 | 查执行证据，不代替真实状态核对 |

一次恢复可以产生新的 trace，却仍属于同一 task。它不应该把几小时的任务硬塞成一条持续打开的调用链。反过来，即使完整 trace 丢失，只要业务状态与回执健全，也不应因此重复保存草稿。观测与恢复相互关联，却是两个不同的正确性问题。

## 文档更新流怎样改变答案

请求流看起来是向前走，知识变化却会影响多个下游副本。假设 C-T20 的下一份修订正式补充了虚拟滚动说明，不能只更新网页正文，然后期待所有答案自然变新。

```text
权威来源变更 / 删除
  → 校验来源修订与权限元数据
  → 构建待发布的文档单元与索引快照
  → 检查完整性、回归题与删除标记
  → 切换有效快照
  → 失效检索缓存、答案缓存及相关引用
  → 新请求使用新快照；旧运行保留当时版本证据
```

本系列没有把“新增虚拟滚动支持”写入原始 `atlas-fixture-01`。上面只是更新情景，若要实践，应建立明确的新资料包版本并修改相应题目的判定依据。否则会出现一种非常隐蔽的错误：程序已经读取了新事实，评测仍使用旧答案，或者评测期待新能力，资料里却没有任何支持。

删除与撤权比修改更严格。不能只等待缓存自然过期；即使已经生成过答案，当前请求也应重新检查权限和来源有效性。失败重建不能把带旧修订的数据重新覆盖到新版本之上。旧运行证据可以按保留政策用于审计，但不应因此重新变成用户可读的知识。

## 可选模块什么时候才值得进入图

记忆适合保存经过允许、带来源和期限的偏好，不适合代替组件权威文档；Skill 适合复用操作步骤，不等于把全部资料塞进提示词；MCP 解决协议接入与发现，不负责替应用决定授权；多 Agent 只有在可独立验收的分工收益超过协调成本时才有意义。

因此架构图里的可选模块应附带触发条件。例如“出现多个客户端重复适配同一工具”才评估 MCP，“固定并行检索仍不能满足独立审阅需求”才比较多 Agent。没有这个条件，图上的空框不算技术债，更不需要为了系列完整而实现。

真实模型与 Langfuse 也遵循同一规则：外部路径有配置示例和自检步骤，但本地 mock 通过不能替它们签字。接入后要重新核对实际模型行为、链路父子关系、脱敏、费用缺失值和关闭刷新，不能把教程里的预期输出复制进运行报告。

## 用一个故障检验这张图

取 Q05：AtlasTable 2.0 是否支持百万行虚拟滚动。先让候选正确包含 C-T20，再给生成结果故意填入“支持”。若系统仅因检索成功就显示任务完成，问题发生在结果检查与评测边界；此时换搜索引擎不能直接解决它。

再把同一题的权限或来源修订改变，检查答案缓存是否失效；最后停止页面等待，检查任务与 UI 是否各自留下真实状态。三次变化只改一个条件，才能知道架构中的每条责任线是否真的生效。

本篇的交付是一张与实际代码相符的架构图，以及一份能从故障现象定位到责任层的说明。下一篇将把启动、测试、未支持范围和恢复限制交给一个没参与写作的人，检查这个系统是否真的可以复现。
