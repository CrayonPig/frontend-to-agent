# 36 流式更快，不代表任务完成更快

用户问“AtlasTable 2.0 怎么设置 rowKey，当前演示构建能用吗？”界面很快开始输出介绍，构建状态却要等工具返回。若前面的文字不能帮助用户决定是否继续，首个字出现得早并没有缩短任务完成时间。

第 06 篇处理了流式状态，第 09 篇建立了预算。现在需要把同一条任务拆开，看等待发生在哪里，再决定优化对象。本篇的产出是一份端到端延迟预算和可以复核的统计口径，不是“打字动画更快”的截图。

## 用同一时钟定义边界

对一次服务端执行，可以记录排队开始、执行开始、检索结束、生成开始、首段输出、工具结束和任务终态。浏览器还可以记录提交与最终展示，但客户端和服务端时钟未必同步，不能直接拿两个机器的墙钟时间相减而不说明误差。

下面是一条人为构造的相对时间线，单位毫秒，仅用于理解，不是实测：

```text
0       接收请求
0–80    排队
80–180  检索授权资料
180–260 重排与证据整理
260–960 组织答案（首段输出在 400）
260–760 查询演示构建状态，与组织资料说明并行
960     合并状态、校验并返回任务终态
```

用户在 400 毫秒看到文字，完整任务在 960 毫秒结束。检索、重排、生成和工具耗时直接相加得到 1380 毫秒，却不是实际墙钟时间，因为其中有并行区间。要沿关键路径找瓶颈，不能把所有子 observation 时长相加当总延迟。

“首个可用信息”还需要业务定义。在这个例子里，带有 C-T20 依据的 rowKey 说明可以先作为部分结果展示；如果用户只问“构建是否可用”，一段组件背景介绍就不算可用信息。观测里的首 token 时间是传输指标，不能自动填进业务指标。

## 一条 trace 没有 p95

p50 表示一组样本的中间位置，p95 描述较慢尾部。先定义样本是什么：同一版本、相同任务类型、某个时间窗内所有已接受请求，还是仅成功回答？超时和取消是否单独统计？若只选最快的成功请求，数字会很好看，却回答不了用户为什么经常等不到结果。

可用一个明确的最近秩算法做教学计算：排序后取 `ceil(p × n)` 对应的元素。下面代码是可复制到 Node.js 的独立 JavaScript 计算示例，不依赖模型或外部服务：

```js
const durations = [120, 150, 170, 180, 190, 200, 210, 240, 400, 900]
function percentile(values, p) {
  if (!values.length || p <= 0 || p > 1) throw new Error('invalid_sample')
  const sorted = [...values].sort((a, b) => a - b)
  return sorted[Math.ceil(p * sorted.length) - 1]
}
console.log(percentile(durations, 0.5), percentile(durations, 0.95))
// 按上述算法预期：190 900；这是合成数组的计算，不是线上性能。
```

仓库 `examples/atlas/governance.mjs` 也提供最近秩 `percentile(samples, p)`，在 `0 < p <= 1` 的有效参数范围内用于合成统计测试；空样本返回 `null`。它不替调用方定义样本窗口，也不是监控平台。

不同统计系统可能采用插值算法，因此报告要写明方法。十个合成值适合验证计算，却不足以证明真实长尾稳定。对生产观察还需固定时间窗、样本量、任务构成和并发条件，并报告未完成任务的数量与等待时长。

## 先判断慢在哪里，再选择手段

如果排队占主要时间，减短输出并不解决容量问题。需要看并发上限、请求到达模式和执行耗时，必要时拒绝超预算请求，避免无限排队。若检索慢，先核查过滤、索引与候选数；不能为了速度取消权限过滤。若重排收益很小却显著增加耗时，就用同一评测集判断是否关闭，而不是因架构图里有这一层就保留。

生成慢时，可以减少无关上下文、约束输出长度或试验模型路由。但删掉 C-B14 会使迁移比较缺少依据，这种“提速”应在质量回归中失败。工具状态查询可以与静态资料整理并行，前提是后者不依赖工具结果；最终结论仍须等待必要结果并标注时效。

前端性能优化擅长拆分关键路径，这个经验仍然有用。边界在于模型输出长度和调用步骤会波动，不能仅靠一次瀑布图推断长期收益。应固定任务集，再比较改动前后的分布与失败率。

## 从这条实际 SDK 链路读取耗时

第 39 篇不再只用手写数字比较 Prompt。独立示例把 A30 分别送入两个实际读取的 Prompt 版本，经本地 HTTP 模型和真实 Langfuse SDK 导出 observation，保留运行时间与 trace。完成第 11 篇的示例安装后，在 `examples/atlas-observability` 执行：

```bash
npm run compare
```

从 `reports/compare.json` 的 `runs` 找到两版各自的 `durationMs`，再用报告中的 trace ID 对照同轮 `reports/compare-spans.json` 的 observation、`parentSpanId` 和阶段 `durationMs`。不要使用另一命令覆盖后的最近快照去匹配旧报告。先定位 `model.answer` 和工具步骤，再回到整个任务耗时。如果根节点比模型 generation 更长，差额可能包含准备、Prompt 读取、工具、校验与调度，不能统称为“模型慢”。分支并行时，仍不能把子步骤相加当作根节点时长。

这份报告是本机合成链路的实际测量，模型输出由 mock 决定，两个版本在对比命令中并发执行，还会受进程冷启动、资源竞争和系统调度影响。它适合检验时钟与字段关联，不适合宣布版本 2 更快。当前演示不是生产并发试验，A30 每版的小样本也不足以估计真实 p95；应报告样本量和实际观测值，把更大样本统计留到受控实验。

本地模型响应不是逐 token 流式响应，因此不能从请求开始到响应结束之间随便选一个时刻称为“首 token”。如果当前报告没有测量首可用信息，就保留未测量状态。之后接入流式供应商时，在适配层真实接收第一个数据块的位置增加事件，再按任务定义单独标记首个可用结果。第 39 篇的质量判定也必须一起看：更早返回“virtual 已支持”仍是更早失败。

## 给预算一个可执行后果

教学预算可以设为“总任务不超过某个上限，工具最多占其中一部分，超时后返回部分可证实的结果和未完成状态”。具体数值应由使用目标决定，本文不把某个秒数宣称为通用标准。预算必须与第 09 篇的截止时间共享，不能每个步骤重新获得完整时长。

观察字段至少有任务类别、执行版本、排队耗时、各阶段耗时、首输出、首可用结果和终态。缺少业务事件时，首可用结果应标未知，不拿首 token 代填。脱敏后保留合成题 ID 或受控分类即可，不必在延迟报表中显示用户问题全文。

一次有效实践是给固定合成任务注入慢检索、慢工具和慢生成，确认记录能指向对应阶段；再让工具与独立资料处理并行，检查总时间不是子步骤之和。验收要同时满足结果仍正确、取消与超时有终态、统计包含失败分母。之后再谈缓存，才知道缓存究竟在节省哪一段等待。
