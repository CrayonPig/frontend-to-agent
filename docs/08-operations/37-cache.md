# 37 缓存命中以后，答案还能不能用

Q03 的答案已经生成过：AtlasButton 1.4 用 `loading` 显示等待图标，`disabled` 阻止 click。下一个人问了几乎相同的问题，直接复用能省调用。但他指定的是 2.0，或者原来的私有资料刚刚撤权，这次命中就可能比一次慢查询更糟。

缓存是复用某次计算的结果，前提是本次依赖仍允许复用。本篇把检索结果、最终答案和模型侧缓存拆开，并用删除与撤权检查正确性。

## 三层缓存保存的东西不同

检索缓存保存候选文档或片段标识，减少重复搜索；答案缓存保存组织后的结论，省掉后续生成；模型侧缓存若供应商提供，可能复用部分输入计算，但不等于应用可以跳过授权与证据选择。第三类能力的具体语义随供应商和版本变化，本教程不假定任何供应商已启用它，也不估算未经测量的收益。

检索命中后仍要检查文档是否存在、版本是否适用、当前身份是否可访问。答案命中要求更强：除了资料有效，生成契约、Prompt 和模型配置可能也属于依赖。一次引用完整但措辞有误的答案，不能因为缓存加速就绕过业务校验。

前端缓存常用 query key 表达依赖。这里继续沿用这个思路，但服务端权限策略和知识代次也必须进入判断。浏览器不能自行声称“我的权限版本还是旧的，所以可以用旧缓存”。

## 先用保守的精确键

下列未运行的 TypeScript 示意强调组成，不规定生产键的编码和散列方式：

```ts
type AnswerCacheKey = {
  tenantId: string
  userId: string
  policyVersion: string
  indexGeneration: string
  question: string
  targetVersion: string
  promptVersion: string
  modelConfigVersion: string
}
```

按用户分开会牺牲命中率，却容易理解与验证。以后若想在等价权限组间共享，要证明组内每个成员对所有来源的权限确实相同，并在成员变化时失效。不能只用角色名，因为同名角色在不同租户或资源上可能有不同范围。

问题文本可以做确定的空白归一化，但不要随意删掉版本数字或否定词。“支持 public 吗”和“不支持 public 吗”可能需要不同解释；“1.4”与“2.0”更不是噪声。语义缓存把相似问题当成同一输入，额外引入正确性风险，应有专门评测，不能由相似度阈值代替事实判断。

缓存值至少包含结果、来源 ID 与修订、创建时间和到期时间。查找顺序可以是：确定当前可信身份及策略版本，构造键，检查有效期，再重新验证所有来源仍可访问且未删除，最后返回。若其中任一步不确定，按未命中处理比返回旧答案安全。

## TTL 不会替你处理撤权

假设某答案来源为本租户的 T-A20，缓存有效期还有十分钟。管理员现在撤销访问，如果系统只等待 TTL（存活时间）到期，就相当于承诺撤权十分钟后才生效。是否允许这种延迟必须是明确产品约定，不能由缓存实现偷偷决定；本系列的权限边界要求当前授权校验，命中不能绕过它。

知识删除也一样。删除事件推进索引代次并作废相关缓存；读路径还检查墓碑或源记录状态，避免失效消息丢失后继续返回。第 20 篇的幂等更新规则仍然适用：旧导入任务迟到，不能把已经删除的资料重新写回。

多版本并存不等于全量失效。更新 2.0 的某份卡片，不一定让 1.4 的所有回答失效；可以按依赖来源做更精细的失效。但先实现粗粒度的 `indexGeneration`，验证正确，再用测量证明细化值得做。复杂失效算法若没有回归，很容易把节省的调用换成难查的旧知识问题。

## 失败答案也要明确策略

“资料不足”可以短期缓存吗？可以作为设计选择，但新资料入库后必须使它失效，否则助手会继续声称没有资料。授权拒绝也不能长期以用户文本为键复用，因为身份和权限可能变化。工具的实时状态应有独立有效期，不能把昨天的成功永久嵌进文档答案。

并发首次请求可能造成缓存击穿：多个相同任务同时计算。可以在同一隔离键上合并在途只读请求，但一个用户取消等待，不应无条件取消其他等待者；失败结果也不能被误存成永久成功。合并请求增加了状态责任，先按第 06 篇的取消与终态规则处理。

## 运行一次删除后的读取

`examples/atlas/governance.mjs` 的内存 `ScopedCache` 把身份、权限、索引代次和调用方输入组成键，并在读取时重验来源。调用方仍需把目标版本、Prompt 与模型配置等实际依赖放进输入，类本身不会猜这些依赖。在仓库根目录运行：

```bash
node --input-type=module <<'JS'
import { ScopedCache } from './examples/atlas/governance.mjs'
import { DocumentStore } from './examples/atlas/core.mjs'
import { principal } from './examples/atlas/fixtures.mjs'
const cache = new ScopedCache()
const store = new DocumentStore()
const input = { question: '等待参数', version: '1.4', promptVersion: '1', modelConfigVersion: 'mock-1' }
cache.set(principal, store, input, { kind: 'answered', sourceIds: ['C-B14'] }, 1000, 0)
console.log(cache.get(principal, store, input, 1)?.kind)
store.apply({ id: 'C-B14', revision: 2, deleted: true })
console.log(cache.get(principal, store, input, 2))
JS
```

预期输出 `answered` 与 `null`。这里的结果只是缓存夹具，省略了答案正文，不能送入问答接口充当合格 `TaskResult`。这次验证证明索引代次变化后旧键失效，不代表实现了分布式缓存、并发合并或模型侧缓存。

## 验收看错误复用，而不只看命中率

以 Q03 和 Q04 检查版本隔离；用 `reader-a` 与另一个合成身份检查跨用户复用；模拟 T-A20 撤权、C-B14 修订、文档删除和资料新增，检查旧结果不再被返回；最后把两个并发相同请求合并，检查每个调用方都有自己的终态。

观测记录缓存层、命中原因、依赖代次、重验结果和节省的阶段即可。不要把隐藏文档名称放在“缓存为何拒绝”日志里；外部响应只需通用说明。命中率只是运维指标，错误复用数必须单独观察。一个始终命中旧答案的缓存可能有完美命中率，却是失败的知识系统。
