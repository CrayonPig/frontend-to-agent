# 40 一次变更如何安全上线

修复 Q03 的 Prompt 已通过离线检查，但同一批发布还更新了索引、工具参数和 Skill。上线后用户得到旧引用，应该退哪一项？如果只知道前端包的 commit，无法判断生成时用了哪个索引代次，也不能确定已写入的迁移草稿会不会被重复保存。

发布对象是一个能共同工作的版本组合。本篇把前面的评测、trace、缓存、恢复与 Prompt 治理连成发布流程；它不要求微服务，也不表示本教程已部署真实助手。

## 先写下能重建的组合

下面是合成发布记录示意，版本标签用于教学，不代表真实线上部署：

```json
{
  "releaseId": "atlas-demo-release-2",
  "applicationRevision": "reviewed-source-revision",
  "prompt": { "name": "atlas-answer", "version": 2 },
  "modelConfigVersion": "mock-config-1",
  "indexGeneration": "atlas-fixture-01-index-2",
  "toolContractVersion": "build-status-1",
  "skillVersion": "skill-atlas-1",
  "evaluationReport": "reviewed-evaluation-report",
  "previousReleaseId": "atlas-demo-release-1",
  "status": "candidate"
}
```

占位字段在实际发布前必须替换为真实标识。记录还应能找到数据迁移、兼容性检查和审批结果。多个版本各自“测试通过”，不代表组合可用：新工具返回结构可能不被旧应用接受，新 Prompt 可能输出旧界面不认识的结果类别。

前端发布清单的经验仍适用，但这里还有状态与外部副作用。回退页面或服务代码，不会自动撤销已创建的草稿；回退索引快照，也不能重新开放已撤销的权限。因此发布记录需要写明哪些变化可以切换指针，哪些需要向前修复。

## 离线门槛先挡住确定的退步

先运行合成题与故障注入，验证格式、事实、引用、拒答、隔离、注入、预算、取消和恢复。安全用例出现新增越权必须阻止候选发布；普通质量与延迟门槛应按业务目标定义，并说明样本数与基线。不能照搬一个成功率阈值后假装它代表所有用户任务。

离线报告要有固定题集版本、候选输出、判定理由与执行版本。开发题用于调试，独立检查题用于发现过拟合；不能反复针对检查题修 Prompt 却继续称它独立。对于外部模型或服务，未运行的集成测试应标出，不可由本地 mock 的通过代替。

再做一次恢复演练：在模拟写入已成功但回执丢失的位置中断，重启后依据幂等键查状态。若回退后的代码读不懂检查点或写入记录，就不是可用退路。发布前发现这种问题，比上线后再讨论数据库回滚便宜得多。

## 小流量验证要有退出机制

真实应用可以把已批准候选放到明确的一小部分任务或内部测试范围，保留旧版本处理其余任务。具体比例、持续时间与可接受风险需要业务决定；本教程不擅自开启真实流量。分配方法要稳定，避免同一长任务执行中途来回切版本。

小流量检查同时看任务质量、权限拒绝、异常率、端到端长尾、成本未知比例和人工接管。观察到 HTTP 错误为零，不能省掉答案抽样。抽样也要说明方式：若专门多看失败案例，可以定位问题，却不能把这个样本的通过率直接当作线上通过率。

告警应能指导动作。比如“引用了不在本次授权集合中的来源”要立刻停止相关路径并排查；“工具偶发超时”可能先按预算返回部分结果；“成本字段大面积缺失”意味着成本结论暂不可用，不是费用突然下降。阈值和响应人应在发布前确定，不能等模型决定是否报警。

## 回滚前区分四种对象

| 对象 | 可采取的退路 | 不能默认成立的事 |
| --- | --- | --- |
| Prompt、模型配置 | 切回已验证的不可变版本 | 标签回退不会立即刷新所有缓存 |
| 索引 | 切回兼容快照或重建 | 快照不能恢复已删除或撤权的资料 |
| 工具执行 | 停止新写入，核对已有回执 | 超时不能直接认定未执行 |
| 任务状态与记忆 | 兼容读取或受控迁移 | 旧代码能理解所有新状态 |

回滚也应产生发布事件，记录原因、受影响任务范围和后续验证。不要为了让面板恢复绿色而删除失败 trace；同时也不能无限保留敏感输入。按保留期留足排查所需的最少证据，真实用户数据应脱敏、限权和按规则删除。

## 把第 39 篇的真实 SDK 变更纳入发布记录

先以一个实际可复现的发布单元开始：在 `examples/atlas-observability` 中，`npm run seed-prompts` 通过真实 Langfuse SDK 的 HTTP 路径创建模板；`npm run compare` 对比两版；`npm run promote -- --version 2 --confirm` 读取报告并调用 Prompt 标签更新 API。默认端点是本地模拟服务，并非替真实生产项目发布。

推广不是“测试脚本返回 true 就上线”。报告要匹配待发布版本、fixture、评分规则和 Prompt 内容摘要；命令还需重新取得候选模板，确认内容没有被替换，再执行标签更新与读回核验。真实组织还需要把操作者认证、审批权限和报告完整性放在受信任服务中；命令行 `--confirm` 只是本地演练中的明确操作意图，不是多用户审批系统。

将此次报告标识、实际 Prompt 版本、模型配置和 trace ID 填进前面的组合记录。先核对版本 1 的故意错误确实被评分发现，再确认版本 2 的候选没有把未知能力补成事实。A30 只验证这条链路，不能代替所有任务、安全题、恢复与独立检查集；真实发布必须扩展门槛，而不是把一个合成样例的通过率当上线资格。

做完推广后运行 `npm run run -- --label production`，从实际请求记录核对解析出的版本。再执行 `npm run rollback -- --version 1 --confirm`，确认标签移动和回退审计留下记录，历史 trace 的版本没有被重写。这里故意回到质量不佳的版本 1，只用于验证配置退路；回退记录应标记它没有获得当前质量批准。生产事故可能需要停用相关能力或切换到另一个已验证版本，不能把这个演练命令机械照搬到真实服务。

当前仓库验证的是 SDK 调用、HTTP API、报告校验与标签变化，不是完整 Langfuse 平台的授权、审计落库和真实流量发布。外部平台配置完成后，还应核对 UI 中对应 Prompt 版本、generation 链接和发布记录，并验证权限与保留期。平台收到数据和模型答对依然是两个判断。

完整发布组合、小流量分配、状态迁移与跨实例缓存刷新仍需按本篇前文实施。尤其不要用“Prompt 已回退”掩盖索引已删除的事实或工具已经产生的副作用。把回退后的运行再次关联到同一发布记录，才能判断恢复的是配置，还是用户任务本身。

下一部分回到请求流和知识更新流，把实际已有模块连起来。架构图应反映这些验证边界，而不是把所有可选能力画成已经上线。
