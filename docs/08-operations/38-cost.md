# 38 不是每次调用便宜，而是每次成功任务划算

一个改动把答案压得很短，每次生成用量下降。评测却发现 Q03 经常漏掉 `disabled`，用户需要追问，部分任务还进入人工处理。如果只展示“平均调用费用下降”，这个优化就把失败成本藏到了报表外面。

本篇要计算的对象是任务，而不只是 generation。先确定哪些结果满足任务，再统计为了这些结果发生的模型、检索、工具、重试和基础设施开销。

## 先分清数量、估算与账单

Token 用量是数量，乘以价格才能得到某种费用估算；供应商直接返回或账单确认的费用，与应用按用量计算的数字也不是同一种来源。若不知道某次请求用了多少 token，费用应是未知，不是零。若只知道模型费用，也不能给它起名叫“系统总成本”。

Langfuse 可以接收用量与费用数据，也支持按模型配置进行费用计算；应保留输入、输出、缓存等用量类别及数据来源。字段与计价能力以官方文档为准，本篇不写死供应商价格。参见 [Token 与费用追踪](https://langfuse.com/docs/observability/features/token-and-cost-tracking)，核对日期：2026-10-26。

一个教学账本可以按 task ID 汇总多个执行尝试：

```text
task-demo-03
  model attempt-1：用量已知，费用为估算
  model attempt-2：用量缺失，费用未知
  retrieval：本地示例不计供应商费用，真实基础设施费用未分摊
  tool：一次只读模拟调用，无真实收费
  task verdict：通过 / 不通过 / 尚未判定
```

“无真实收费”描述本地模拟没有付费调用，不意味着运行机器、电力和维护免费。真实系统可以先明确只报告直接可归属成本，未纳入的部分列为范围限制，再逐步补充分摊，而不是假装一开始就得到精确总账。

## 分母必须由评测决定

下面是一组人为构造的抽象成本单位，不是价格或模型实测：方案 A 处理十个任务，消耗 100 单位，八个通过；方案 B 消耗 80 单位，只有五个通过。每个通过任务对应的总消耗分别是 12.5 与 16。B 每次请求便宜，却没有更划算。

计算时，总消耗要包含失败尝试，否则会把失败造成的浪费删掉。准确拒答在对应题目上也可能是通过，但不能为了增加通过数，把原本应该有依据回答的题目都拒绝掉。Q05 的资料不足是合格结果，Q03 有 C-B14 时仍拒答则未完成。通过定义必须沿用评测规则。

当存在未知费用时，可以报告“已知费用小计”和“未知项数”，完整的每成功任务成本暂记未知。下面是未运行的 TypeScript 示意：

```ts
function costPerSuccess(costs: Array<number | null>, successes: number) {
  const knownSubtotal = costs.reduce<number>((sum, c) => sum + (c ?? 0), 0)
  const unknownCount = costs.filter(c => c === null).length
  return {
    knownSubtotal,
    unknownCount,
    completeCostPerSuccess:
      unknownCount === 0 && successes > 0 ? knownSubtotal / successes : null,
  }
}
```

仓库中的同类实现可直接验证未知值传播。在根目录运行：

```bash
node --input-type=module <<'JS'
import { costSummary } from './examples/atlas/governance.mjs'
console.log(costSummary([{ cost: 10, pass: true }, { cost: null, pass: false }]))
JS
```

预期包含 `total: null`、`knownSubtotal: 10`、`unknownCount: 1`、`successfulTasks: 1`、`costPerSuccess: null`。抽象成本单位不对应真实币种。`pass` 必须来自外部评测，汇总函数不会判断回答质量。

没有成功任务时，分母为零也不能输出 0；那是“无法得到有限的成功成本”，需要查看失败原因。货币、税费、账单时间窗与分摊规则不同的数值不能直接相加。

## 优化是质量、延迟和成本的联合实验

对精确参数解释采用较小的模型，对资料冲突保留更严格的流程，是一种待验证路由假设，不是“简单问题一定可以用便宜模型”的事实。路由器本身会误判，需要把路由选择记录下来，并比较各题型失败。

上下文裁剪可能减少输入消耗，也可能删掉目标版本；关闭重排可能省一步，也可能让相关证据排不到前面；固定流程回退能限制循环次数，但不能跳过必需澄清。每次只改一个主要因素，保持题集与资料快照一致，再看结果。若同时换模型、Prompt、索引和候选数，即使总成本下降，也难以知道是谁造成质量变化。

预算要在执行前有约束，在执行后有对账。第 27 篇的步数上限防止无限循环，但不自动等于费用上限；不同调用的输入长度和模型计价可能不同。实际费用无法预知时，可用保守估算控制准入，完成后记录实际或未知值。超时不代表远端没有消耗，这类尝试也应保留，不能从账本消失。

## 把 Prompt 对比报告接到账本

在 `examples/atlas-observability` 运行 `npm run compare`，第 39 篇会通过 SDK 读取两版 Prompt，并把同一 A30 任务的质量、耗时和费用记录放进 `reports/compare.json`，逐次运行证据位于对比报告的 `runs`，独立 `run` 命令保存在 `reports/run.json`。这个数据源比手填“本次成功、费用为零”更有约束：候选答案经过规则判定，Prompt 版本来自实际读取对象，generation 的用量来自适配器可获得的响应。

默认本地 HTTP mock 不返回 token 用量，所以报告中 `usage: null`，不能用字符串长度补一个数再乘以真实供应商价目表。实验也没有实际模型账单，`cost: null` 保留未知；完整成本和每成功任务成本也应为未知，而不是因未收费写为零。读取时先看费用来源和缺失项，再看质量分母，不要只盯汇总数字。

本例有意让版本 1 的答案把构建成功错误外推成 virtual 支持；即使它用量更少，也不能进入“通过任务”分母。版本 2 的正确结果是演示响应，不证明一次 Prompt 编辑能带来同样的真实模型改善。两版对比验证的是：质量失败会影响成本解释，未知费用不会被算成免费，报告可以沿 trace 找到具体 generation 和调用配置。

连接真实适配器后，需要再次核对返回的用量类型、计费来源和币种，并把重试与工具开销归到同一个 task ID。应用本地报告与 Langfuse 侧按模型定义推算的费用可能不同，不能默默覆盖；应明确记录直接上报还是估算，以及费率版本。Prompt 内容、模型配置或裁剪规则一旦改变，就重新评测，不能沿用旧版的成功分母。

## 让报告能支持决策

一份有用的比较至少包含题集版本、样本数、成功定义、禁止行为计数、端到端延迟分布、已知费用、未知比例、成本来源和未纳入项。不能只挑成功 trace 做费用平均，也不能把保留更多失败的观测抽样直接当作总体任务分布。

实践时先用上述十任务合成账本核对公式，再加入一个费用未知的尝试和一次失败重试。预期是完整单位成本变为未知，已知小计仍保留，失败尝试仍计入消耗。随后对真实可选调用再测量，报告中分开写“本地算术验证”与“供应商实测”。本系列默认不调用付费模型。

成本优化的结论可以是“暂不切换”。如果省下的费用不足以覆盖质量下降和接管增加，保留原方案就是基于证据的工程选择。
