# 13 文档放进 Prompt 就够了吗

第一版问答已经能接收资料、返回结构化结果，也能留下运行记录。此时回答 Q03 并不需要搜索系统：把 AtlasButton 1.4 的 C-B14 放进请求，模型就有了判断 `loading` 和 `disabled` 的依据。新增检索之前，先承认这个直接方案在小范围内成立。

真正的变化发生在资料选择上。用户可能问按钮、表格，也可能问 share；还有版本、租户和权限约束。如果每次都把全部资料发出去，问题不只是占用更多上下文。无权读取的 T-B20 不应出现在 reader-a 的输入中；Q14 的冲突卡也不应混进普通题目。系统需要先决定“这次允许且需要看什么”，再决定“怎么回答”。本篇的成果是一份知识获取决策，而不是立即安装向量数据库。

## 先看直接提供材料的成本

对固定的 Q03，输入依赖很清楚：用户指定 Atlas UI 1.4，任务是等待时显示图标并阻止点击，授权后可使用 C-B14。服务端可以按组件名和版本直接取卡片。这里的查找甚至只是字典访问，不必称为复杂检索。

直接输入的优点是依赖少，容易人工复核：如果答案用了 `pending`，检查者可以立刻看出它没有遵循 C-B14。缺点也很具体：应用必须事先知道需要哪张卡；资料变多后，不能把维护选择规则的困难转嫁给模型。把十万字贴入 Prompt 并不会自动建立正确的来源关系。

可以用下面这个未运行的 TypeScript 示意表达当前选择。`authorize` 和 `loadExact` 是应用边界，并非某个 SDK 的方法：

```ts
async function prepareExact(request: RequestInput, identity: Identity) {
  const scope = authorize(identity)
  if (!request.version) return { kind: 'needs_clarification' }
  const docs = await loadExact({
    product: request.product,
    component: request.component,
    version: request.version,
    scope
  })
  return { kind: 'prepared', docs }
}
```

这里最重要的不是函数名，而是顺序：身份确定访问范围，版本确定事实范围，最后才形成模型材料。空结果不能自动改为“查最新版本”；它应进入资料不足的分支。否则 Q06 的 1.8 问题，会被一个看似聪明的兜底悄悄改写。

## 什么时候需要 RAG

检索增强生成（Retrieval-Augmented Generation，RAG）把“按问题找材料”放在“生成回答”之前。它没有让模型获得永久的新知识，而是在当前请求中提供一组外部证据。下一次请求仍然需要按当时的身份、版本和资料状态重新选择。

在 Atlas 助手中，RAG 最先解决的是用户表达不再等于文档路径。例如“显示很多条记录该选什么”，问题没有直接写 AtlasTable；单纯按组件名取卡片就不够用了。检索负责找候选，回答阶段负责使用候选，二者的失败应分开记录。找到了 C-T20 只说明得到了相关材料，不能因此回答它支持百万行虚拟滚动。

可以用三个维度判断是否值得引入：

| 条件 | 更简单的起点 | 需要重新考虑的信号 |
| --- | --- | --- |
| 资料范围 | 单一组件、少量固定版本，直接取材料 | 用户问题无法直接映射到文档 |
| 更新频率 | 每次从权威源取当前修订 | 多来源、多版本，需维护检索索引 |
| 证据要求 | 返回几张明确卡片即可核对 | 需要覆盖多项断言，并定位来源片段 |

“文档很多”只是信号之一，不是唯一门槛。有些小资料集因为权限与版本组合复杂，也需要显式选择；有些大文档任务已由用户指定文件，仍可以直接读取目标部分。衡量的是选择是否可靠和成本是否可接受，而不是有没有采用某个架构名词。

## 改行为，不等于存事实

Prompt 可以说明“证据不足时不要补全”，也可以用例子展示预期格式，但它不是版本数据库。调整模型行为的训练方式同样不能替代实时资料来源：即使模型学会了项目常用的解释语气，也不能据此证明今天某个租户启用了 share。

这里有三个不同问题：表达方式是否稳定、信息是否在当前材料里、信息是否被正确使用。前者可以从提示词和模型能力入手；第二个需要数据源与选择机制；第三个需要证据检查和评测。把三个问题都归为“模型不够聪明”，通常会让改进无法定位。

也不要把直接输入与检索当成互斥产品。可以给精确组件问题走直接查找，给用途描述走关键词召回，再统一生成带依据的答案。只要两条路径共享授权、版本和结果契约，就不必为了架构整齐把每个问题都送进同一个昂贵流程。

## 让选择成为接口，而不是分散的条件

如果直接取卡与检索分别散落在页面、模型适配器和工具代码里，同一个问题很容易得到不同授权规则。可以在服务端把知识选择抽成单一接口：输入可信身份、目标版本与问题，输出允许证据和选择状态。页面不决定读哪个租户，模型也不能传回一段未经校验的数据库查询。

这个接口还应明确失败语义。“没有适用文档”是一次正常选择结果，“知识服务连接失败”则不能当成没有知识。前者让用户补资料，后者可以在预算内重试或提示暂时不可用。只有两者分开，后续才能评估到底是资料覆盖不够，还是基础设施故障。

本仓库的 `examples/atlas/core.mjs` 采用内存文档集合与确定性关键词规则，直接展示这条边界。它不是自动理解任意用户问题的模型，也不包含向量数据库。先用这个替身验证数据流，再决定是否接真实服务，可以避免把账号配置错误与知识选择错误混在一起。

## 做一次不会误导人的比较

用 Q03、Q05、Q06 和 Q13 做四行方案记录。直接提供资料的版本由测试者选卡；自动选择的版本由程序找卡。两者使用同一问题、同一允许范围和同一答案判定规则。分别记下材料数量、是否含所需证据、最终结果类别，以及实际测量的耗时；没有接模型时就把生成质量和费用标为未测。

预期应保持不变：Q03 能依据 C-B14 回答；Q05 找到 C-T20 后仍需说明未知；Q06 不得拿 1.4 或 2.0 冒充 1.8；Q13 只使用当前租户 T-A20。若一个方案回答得更长，却混入跨版本信息，它不是进步。

本阶段的决策可以写为：“精确组件与版本先直接查卡；用途类问题增加关键词检索；保留固定题目检查选择和生成两层。”这是一条可被后续证据推翻的工程决定，不是 RAG 必须采用的通用配方。下一篇先把卡片整理成不会丢失版本与权限的单元，搜索算法暂时还不是重点。
