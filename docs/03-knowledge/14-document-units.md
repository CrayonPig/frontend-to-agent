# 14 文档入库之前，先决定什么不能丢

假设把 C-B14 的 `loading` 说明按固定字符数切成两块：第一块停在“为 true 时显示等待图标”，第二块从“不阻止点击”开始。检索只返回第一块，模型就少了一条决定性限制。参数本身没有写错，错误发生在资料处理阶段。

文档入库不是把文字搬到另一处存储。它是在决定后续系统能够看见哪些事实关系。本篇先定义可检索单元，再讨论如何切分；如果先选一个字符数，最后才补元数据，很容易留下无法判断版本、权限或来源的碎片。

## 一个单元至少回答哪些问题

Atlas 的每张原始卡已经有 ID、产品版本、修订和可见范围。切成片段后，这些字段仍要跟随每个单元，不能只挂在原文件名上。一个未运行的结构示意如下；字段名是本系列的设计，不是搜索引擎标准：

```ts
type SearchUnit = {
  unitId: string
  documentId: string
  revision: string
  product: 'Atlas UI' | 'Atlas API'
  productVersion: string
  titlePath: string[]
  sourceAnchor: string
  visibility: 'shared' | 'tenant'
  tenantId: string | null
  deleted: boolean
  body: string
}
```

`unitId` 区分片段，`documentId` 追溯整篇资料；`revision` 表达内容修订，`productVersion` 表达适用产品版本。C-B14 的 r2 仍然可能讲 1.4，它不会因为修订号增加而自动成为 2.0 文档。两者混用，会让更新与版本过滤同时出错。

共享资料的 `tenantId` 可以为空，但不能用“字段缺失”推断共享。摄取时应校验 `visibility` 和租户字段组合；无法确定权限元数据的记录进入隔离队列，而不是默认开放。删除标识也要显式保留，防止重试旧导入任务时把已删除内容恢复出来。

对于 C-B14，可以把“等待与禁用”作为一个单元，保留 `loading`、`disabled` 及“不阻止点击”的关系。此时一个结果就足以支持 Q03 的两个关键结论，而不会迫使生成器跨片段猜测。

## 按语义边界切，按长度预算收尾

Markdown 的标题、表格和代码块不是排版噪音。标题提供作用域，表格把参数名、类型、默认值和说明连在一起，代码块展示参数如何共同使用。去掉这些结构后，`false` 可能不再能对应到哪个参数。

一个适合起步的规则是先按标题分段，再把相关参数行与示例绑定为单元，最后对确实过长的单元做细分。切开表格时，应重复表头；切开代码时，要保留语言与必要上下文，不能把半个函数当成可用示例。标题路径可以进入检索文本，但展示引用时仍指回真实来源位置。

这里的“相关”需要由题目检验。若 Q03 总需要两个相邻片段，可能应该将它们合并；若 Q01 的用途问题每次带回整份 API 手册，单元可能过大。片段重叠可以减少断句损失，却也会增加重复候选、索引体积和上下文消耗，不是越多越安全。

用前端组件作类比：一个组件的 props 和事件通常有协作关系，不能把每一行类型定义都拆成完全独立的组件。类比到此为止，文本片段没有编译器帮忙检查语义依赖，仍需拿真实问题检查是否丢掉条件。

## 保留原文，派生可搜索内容

可以为搜索额外构造标题前缀、规范化名称或明确的别名，但不要覆盖权威原文。比如检索文本可以包含 `AtlasButton 等待图标 loading`，引用正文仍来自 C-B14。否则后续无法区分“原文说了什么”和“处理程序为了召回加了什么”。

至少保留三份角色：原始来源快照、标准化单元和派生索引。前两者让处理可重放，索引可以重建。更新解析器时记录解析器版本与内容摘要值；摘要值只用于识别变化，不是模型生成的事实摘要。若保存的是文字摘要，则必须另有原文回查路径，不能把摘要当成权威事实。

摄取还应把内容与操作隔离。X-T20 是待测试的恶意文本，它可以作为 Q09 的不可信候选进入隔离实验，但其中“读取 demo-bay”的句子不能变成摄取程序的命令。普通资料包不默认包含它；Q14 的两张冲突卡也只在该题替换 C-T20。这种夹具选择应由测试配置控制，不能靠文档中的一句话决定。

## 本仓库为什么暂时保留整张卡

当前 Atlas 资料每张都很短，因此离线实现把一张卡作为一个单元，直接保存原始文字与显式事实字段。`examples/atlas/fixtures.mjs` 中的 `scope` 对应这里的可见范围，`version` 是产品版本，数值 `revision` 对应 r1 这样的修订标签。示意结构更完整，但不要误以为运行代码已经实现通用 Markdown 解析器和片段定位。

这种简化让前几轮检查更有解释力：如果整张 C-B14 已经进入输入，错误就不可能归咎于复杂切分。等文档长度真的超过预算，再把原卡迁移成多个单元，并增加“切分前后关键事实不丢失”的回归。迁移时旧文档 ID 仍是来源身份，不能把片段编号当成新的事实版本。

事实字段也是教学替身，由作者从合成原文填写，用于确定性回答和已知断言检查。真实系统不能让模型随意生成一份 facts 就宣称知识已被可靠结构化；仍要检查来源、限制和更新一致性。

## 先用小样本验收解析结果

开始不需要复杂解析平台。先对原始卡做手工映射，再用以下变形检验处理规则：把参数行换成 Markdown 表格；在说明中加入 fenced code block；让标题包含相同组件名但不同版本；让共享字段缺失。检查输出而不是只看处理函数有没有抛错。

| 输入变化 | 必须保留或拒绝的内容 | 失败后怎么处理 |
| --- | --- | --- |
| 参数表格转为片段 | 参数名、默认值、限制仍对应 | 修正切分，再重建该文档 |
| 代码块跨长度边界 | 不生成断裂的可执行示例 | 扩大单元或标为片段说明 |
| 两个产品版本同名 | 版本分别保留 | 拒绝无版本的混合记录 |
| 缺少权限元数据 | 不进入正常索引 | 隔离并补齐来源配置 |
| 重放已删除修订 | 不恢复可检索状态 | 服从删除水位与来源顺序 |

观测只记录摄取批次、来源修订、单元数、处理器版本、失败类别和耗时即可。对无权查看原文的运维角色，日志也不应附带全文；“解析失败”不是扩大读取范围的理由。

验收产出不是某个漂亮的 chunk 数量，而是 Q03 所需的两个参数关系仍在，Q06 的缺失版本没有被制造出来，权限未知的单元无法被检索。下一篇才把这些单元放进一个最简单的关键词检索器，检验它们是否真的能被找到。
