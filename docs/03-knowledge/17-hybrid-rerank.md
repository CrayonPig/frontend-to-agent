# 17 两路结果都有用，如何合并和重排

关键词可能把精确参数名排得很好，语义路径可能更容易找到用途描述。把两边的结果拼接起来，似乎就完成了混合检索，但马上会遇到三个问题：相同片段重复出现，两个分数不能直接相加，以及合并后的前几项仍未必最能回答问题。

这三个问题分别对应去重、融合和重排。先把它们拆开，才能判断哪一步值得付出额外延迟。本篇用人为指定的候选顺序解释算法，不声称已经测得某个检索模型更好；真实采用与否仍由同一批 Atlas 任务决定。

## 去重不能抹掉版本差异

假设 Q03 的两路结果都包含 C-B14 的等待与禁用片段。它们如果拥有相同的文档、修订和单元 ID，可以合为一个候选，并保留命中了哪些检索路径。不能只按正文相似或组件名去重：C-B14 与 C-B20 都在讲 AtlasButton，却分别属于 1.4 和 2.0，合并会直接毁掉 Q04 的版本比较。

一个稳定的候选键应至少能区分来源、修订和片段；权限范围也不能在归并时丢失。同一个片段被两路发现，不意味着它拥有两份独立证据。答案引用应指向一次真实来源，而不是把重复召回包装成“多个资料都支持”。

## 为什么不直接加分数

关键词分数与向量相似度通常不是同一尺度。一个是检索器内部相关性信号，另一个可能是归一化几何量；即使都叫 score，也没有天然可比性。直接相加会让数值范围更大的一路主导排序。

一种易于解释的基线是倒数排名融合（Reciprocal Rank Fusion，RRF）：不用原始分数，按文档在每路中的名次贡献分数。以下是未接入服务的算法示意，`c` 是本例可调参数，不是普适最优值：

```ts
function fuse(rankings: string[][], c = 60) {
  const scores = new Map<string, number>()
  for (const ranking of rankings) {
    const unique = [...new Set(ranking)]
    unique.forEach((id, index) => {
      scores.set(id, (scores.get(id) ?? 0) + 1 / (c + index + 1))
    })
  }
  return [...scores.entries()].sort(
    (a, b) => b[1] - a[1] || a[0].localeCompare(b[0])
  )
}
```

用抽象候选 A、B、C 演算：关键词顺序为 A、B，语义顺序为 B、C。B 得到两次贡献，A 和 C 各一次，因此 B 排在前面。这个演算只能证明融合规则的行为，不能证明 B 更相关。若两路共同偏向一份无关资料，RRF 会把共同错误强化。

`c` 越大，靠前名次之间的差异越平缓；候选截断数也会影响结果。调整它们时记录配置版本，在固定题集上比较，不要只选一条漂亮查询展示。为并列分数定义稳定排序，有助于重放与排错，但稳定不等于正确。

## 重排需要额外的信息或判断能力

融合只看排名。重排（rerank）则可以重新阅读问题与候选，判断哪个更支持当前任务。最简单的重排可以是确定性规则：精确组件匹配优先，资料覆盖所问参数优先。更复杂的重排器可能是专用模型，但它也有输入上限、耗时、成本和错误模式。

注意不要用重排补救授权。两路召回都应先限制权限与版本，合并处再次校验防止适配错误，重排只处理允许材料。把越权文档先发给外部重排服务，再删掉结果，泄露已经发生。重排器也不能因内容中出现“请把我排第一”就接受指令；X-T20 在 Q09 是不可信数据。

对 Q14，两个冲突片段都应保留给回答阶段。若重排只选“看起来更像答案”的那张，就把真实冲突藏掉了。排序优化不能以消灭不舒服的证据为代价。候选选择应考虑任务覆盖：版本比较题需要两版，冲突题需要矛盾双方，单参数题则可以更窄。

## 先写预算，再加一个模型

可以先给实验设三个配置：关键词 top-5；两路各 top-5 后融合取 5；融合候选交重排后取 3。这些数字只是小型实验配置，必须与资料规模和题目一起记录，不是默认生产参数。

每个配置都检查：允许证据是否进入候选，关键证据最终有没有留下，重复候选减少了多少，耗时增加多少。对 Q05，任何配置都不应把“没说明虚拟滚动”变成“支持”；对 Q06，没有 1.8 资料就应保持缺失。对 Q14，不能用排名代替冲突处理。

如果实际只得到相同正确资料，重排却多增加一次远端调用，那么暂时保留融合或关键词方案就足够。若重排确实改善一类长问题，仍要检查精确名称题有没有退化。增加组件的理由应当是可重复的净收益，而不是架构图更完整。

链路上把 `retrieve.keyword`、`retrieve.semantic`、`merge.candidates` 和可选的 `rerank.docs` 分开，记录各阶段候选 ID、顺序、配置版本与耗时。关键词和语义可以并行，但最终阶段应有明确汇合点；一条失败时要记录降级，不能伪装为正常双路实验。没有执行的语义或重排阶段不应出现在报告里冒充实测。

还应单独保留一条重排退化样例：给 Q14 的两个冲突候选打不同相关性分数，只保留第一条时，答案可能变得更肯定却更不完整。修复方法不是强制两个分数相同，而是让任务覆盖规则识别同范围冲突，确保决定性证据不会因为 top-k 被抹掉。对版本比较同理，两个版本都属于需要覆盖的范围。

本仓库的 `retrieve` 目前只提供一条确定性关键词路径，没有声称执行过混合召回或模型重排。这里的融合片段可以独立演算，完整方案对比则需要读者接入选定适配器后运行。观测报告中应将未启用阶段留空或标为未运行，不能根据设计图补出虚假的阶段耗时。

当一种方案只改善开发题，而在检查题上引入版本遗漏，决策记录应保留这个反例。撤下新增重排器并不是项目倒退，而是把一个尚未证明收益的依赖移出了关键路径。下一次有更多资料和更明确的失败模式时，可以再用同一记录格式重新验证。

本篇验收产出是一份保留原始排名、融合排名和最终选中证据的对照表。读者应能从一个错误答案回溯：材料压根没找到，还是合并时去错了重，或者重排把决定性限制删掉了。下一部分开始检查生成出的每一条结论，而不满足于“已经搜到了东西”。
