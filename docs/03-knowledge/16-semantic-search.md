# 16 名字不同、意思相近，怎么找到相关资料

“我想把一批记录按字段排成行列”，可能是在找 AtlasTable，但问题里没有出现组件名。关键词基线能处理文档里的“按列展示记录”，遇到换一种说法就可能漏掉。此时才有一个明确理由引入语义表示：帮助不同用词的需求与文档进入同一候选集合。

Embedding 通常译为嵌入，是把文本映射为数值向量的表示。向量里的每个维度一般不能直接解释成一个业务属性；通过训练，相关文本可能在选定距离或相似度下更接近。检索使用这种接近关系找候选，不是在读取模型心中的事实数据库。

## 一个几何演示能说明什么

先不用真实 embedding 服务。下面是可以独立运行的 JavaScript 几何演示，向量由作者手工指定，只演示余弦相似度计算，不代表任何模型的语义效果：

```js
const cosine = (a, b) => {
  const dot = a.reduce((s, x, i) => s + x * b[i], 0)
  const length = v => Math.sqrt(v.reduce((s, x) => s + x * x, 0))
  if (!length(a) || !length(b)) throw new Error('zero vector')
  return dot / (length(a) * length(b))
}
const query = [1, 0]
const candidates = [
  { id: 'table-purpose', vector: [0.9, 0.1] },
  { id: 'button-purpose', vector: [0.1, 0.9] }
]
console.log(candidates.map(x => ({
  id: x.id, score: cosine(query, x.vector).toFixed(3)
})))
```

这段计算的预期值分别约为 `0.994` 和 `0.110`。它只说明在我们给定的几何关系里，第一项更接近。不能把这两个数写进“Atlas 检索提升报告”，因为向量关系本身就是人为设定的。真实模型是否把“行列展示”与 C-T20 拉近，必须在选定模型、输入处理和版本下实测。

这里也能看见一个危险：若把一段无依据的“支持百万行”赋成接近的向量，它仍会排得很高。相似计算不会检查断言真假，也不会发现这个能力在 C-T20 中其实未知。

## 向量空间是一个版本化依赖

真实接入时，要记录 embedding 模型及版本、维数、预处理方式和索引代次。问题与文档必须按兼容的表示方式编码。只更新查询模型、不重建旧文档向量，即使维数相同，两个空间也未必可以比较；维数不同更应立即拒绝，而不是补零凑齐。

文档向量通常可在摄取阶段生成，查询向量在请求时生成。前者跟随文档修订更新，后者受单次任务预算限制。若嵌入服务失败，不能把“查询向量为空”解释成“没有相关知识”；可以明确降级为已验证的关键词路径，并记录降级原因。

这与前端构建产物有一点相似：源文件变了，派生文件需要重新生成。但类比不能继续到“编译通过即可保证行为”。向量是压缩后的检索表示，不保留完整事实关系，也不会给出编译式正确性保证。生成器仍须读取原始可引用文本。

## 权限与版本不能交给相似度

语义搜索也需要先限制允许候选。reader-a 的问题不应与 T-B20 的私有正文产生可返回匹配；Q06 指定 1.8，也不能因为 2.0 内容很相似就拿它作答。在本地小数据上，可以先过滤再计算距离；在搜索服务中，要确认选择的接口确实支持所需的过滤位置。

例如 Elasticsearch 8.19 的 kNN 查询区分预过滤与后过滤；应用需要理解过滤在哪一阶段执行，不能在取回全库最近邻以后才让模型删除越权项。若只在 top-k 后过滤，还可能得到很少甚至零个结果，因为有权访问的文档根本没有进入最初的候选。官方也建议一般近似 kNN 搜索使用搜索请求的顶层 kNN 部分；具体接口需按部署版本验证。本篇不提供未经运行验证的向量集群配置。[官方 kNN 文档，核对于 2026-10-26](https://www.elastic.co/guide/en/elasticsearch/reference/8.19/query-dsl-knn-query.html)

真实系统可以进一步采用租户分区或专用索引，但这些是隔离策略选择，不会免除服务端授权。索引里有 ACL 字段不代表查询真的用了它，必须检查执行路径与测试结果。

## 先保留一种可以解释的退路

如果用途题在关键词路径找不到，而语义路径返回两段只在语气上接近的资料，系统仍然可以给出资料不足。没有候选比给出不适用证据更容易处理。不要为了维持某个命中率，在相似度太低时自动放宽版本；这样改变了任务而不是改善了检索。

也不建议直接复制别的项目的相似度阈值。距离定义、模型、文本长度和语料分布都会影响数值含义，阈值需要在本任务的正例、未知例和相近错例上校准，并观察误拒与误接纳。若样本太少，先把分数当排序信号，保留人工判定，不伪装成概率。

本文的几何数值已在本地执行得到 0.994 与 0.110；但仓库主线没有真实 embedding 或近似向量索引。只有计算示例被验证，语义召回提升仍待外部实验。把这两种证据分开，是为了让读者知道接下来需要测什么。

## 给两种方法同一场考试

从现有题目派生一个明确标为开发样例的改写集合：Q01 的原问法和“记录按字段排成行列”；Q03 的精确 `loading` 问法和“按钮显示等待同时不能点”；再保留 Q06 的缺失版本作为负例。原题 ID 不变，改写加独立标识，例如 `Q01-paraphrase-a`，避免覆盖原始基线。

对每个查询，记录关键词与语义候选前 k 项、正确资料是否出现、排名和耗时。两路要使用同一授权范围、资料快照和目标版本，否则比较的不是检索策略。不要用不同大小的候选集合宣布某一路召回更好，而不交代额外上下文成本。

预期假设是语义路径可能帮助用途改写，关键词路径可能更擅长精确参数名。这里没有真实 embedding 实测，所以应保留为假设，不能写成结论。若实际结果是关键词已覆盖所有需求，暂不引入向量同样是合理产出。

验收还应故意加入一个空向量、一个不兼容版本和一个跨租户候选，确认错误不被悄悄转换成相关性结果。记录中保留表示版本、候选 ID 与相似度即可，不需要记录全部向量或私有原文。下一篇考虑两路各有优势时怎样合并，但先记住：多一条召回路径，也多了一条必须接受权限和评测约束的数据路径。
