# 25 从只读到写操作：预览、确认与幂等

前一版已经能给出迁移建议。用户接着说：“把这份建议保存成草稿。”这次与查询构建不同：系统将新增一条记录。若网络超时后重试，可能保存两份；若用户在预览后改了内容，确认按钮可能批准了另一份；若权限已经变化，昨日的确认也不应继续有效。

本篇只在合成沙箱中模拟保存迁移草稿，不修改真实仓库，不发送消息，不执行 `share`，也不访问设备位置。成果不是“助手能写入”这一句演示，而是能说明一次写入由什么授权、如何防止重复，以及不知道结果时怎样处理。

## 预览先固定“这一次”变更

用户允许保存建议，不代表允许模型临时添加任何内容。预览应展示目标、内容及影响，并由服务端保存一个待确认记录。浏览器显示的文本只是预览表现，执行端不能在收到 `confirmed: true` 后信任另一份任意正文。

下面是预览记录的 TypeScript 设计示意，字段表达的是生产实现应检查的边界，不代表教学沙箱已经提供数据库与完整身份服务：

```ts
type DraftPreview = {
  previewId: string
  taskId: string
  tenantId: string
  actorId: string
  contentHash: string
  targetVersion: string
  permissionRevision: string
  expiresAt: string
  state: 'awaiting_confirmation' | 'consumed' | 'expired'
}
```

`contentHash` 绑定确定内容，防止确认之后换正文；`taskId` 防止把另一个任务的确认拿来使用；身份、租户和权限修订说明谁能批准这次操作；有效期限制确认被长期滞留。哈希不是加密，不能把敏感文本的哈希当作绝对无泄露信息，日志仍要按敏感程度控制。

示例预览可以是：“将在当前合成租户保存迁移草稿：AtlasButton 1.4 的 loading 改为 2.0 的 pending，保留 disabled 的独立行为。不会修改源码，也不会发布。”这段说明把资源变化和不会发生的外部操作明确分开，用户才知道确认的对象。

## 确认由服务端核对，不由模型宣告

确认请求应携带预览 ID、内容摘要及幂等键；身份来自可信会话。服务端重新检查当前权限，读取存储的预览，核对内容、任务、有效期和状态，再进行写入。模型不能把工具结果里的“用户已确认”作为真正确认事件；浏览器隐藏了确认按钮也不是授权边界。

幂等键标识一次逻辑操作。对同一用户、租户、任务与内容的重复提交，系统返回同一结果；如果同一个键被用来提交不同内容，应报告冲突，不能静默覆盖。幂等键不是“每次点击都随机生成一个新值”，否则网络重试仍会创建第二份记录。

关键顺序可以写成下面的事务伪代码：

```text
读取可信身份并重新授权
读取并锁定待确认预览
核对任务、内容、有效期
查找该作用域中的幂等记录
  已存在且内容一致 → 返回已保存结果
  已存在但内容不同 → 拒绝冲突
在同一事务中：保存草稿 + 保存幂等结果 + 消费预览
提交后返回草稿标识
```

仅仅执行“先查有没有，再插入”并不安全：两个并发请求可能同时查到没有。真实存储需要唯一约束或原子事务保证；内存中的顺序示例只说明协议，不能证明多进程安全。教学沙箱用小规模合成状态演示重复请求语义，生产实现应单独验证并发与崩溃窗口。

## 超时以后，先查询状态

最容易出问题的时刻是：草稿已经保存，响应还没到浏览器，连接断了。页面只知道没有收到回执，不知道服务端是否执行。此时显示“保存失败，重新创建”会诱导重复操作。

更准确的状态是 `outcome_unknown`，即结果待核对。使用同一作用域和幂等键查询操作记录：若已经完成，取回原草稿 ID；若明确没有执行，再按契约决定能否重试；如果状态服务也不可用，保留待核对状态，不宣称未写入。

这里的查询必须同样授权。知道一个幂等键不能获得读取别人草稿的能力；撤权之后，即使此前操作成功，也不能向当前无权用户披露内容。可以给用户一般性的处理提示，由具备权限的流程进一步核对。

也不要把“支持删除草稿”叫作万能补偿。创建通知、发送邮件、调用第三方后，即使删除本地记录，也无法让对方忘记已经看到的内容。副作用的可逆性是业务事实，需要逐项证明，不能由重试框架保证。

## 沙箱中应该看见哪些结果

保留以下测试顺序：先生成预览，未确认就尝试保存；确认一次后再重复同一请求；用同一个幂等键替换内容；在写入成功后模拟丢失响应，再查询原操作。预期分别是拒绝、返回同一草稿、拒绝冲突、恢复同一草稿标识。

再补两个跨边界失败：另一个用户不能消费这份预览，权限改变后旧确认失效。教学适配器若尚未实现某一项，应在覆盖记录中列成未实现的生产要求，而不是让一次成功演示代表全部边界通过。验收时同时检查记录数，不能只比较两次响应文本相同；响应相同仍可能背后创建了重复数据。

审计记录需要操作 ID、预览摘要、确认主体的受控标识、结果与时间，帮助回答“谁批准了哪一份变更”。普通观测 trace 记录状态和耗时即可，不必复制完整草稿。审计与 trace 可以关联，但访问范围、保留时间和删除规则不必相同。

实际沙箱代码是 `examples/atlas/execution.mjs` 中的 `DraftStore`：`preview` 生成待确认记录，`confirm` 保存回执，`lookup` 查原幂等结果，`snapshot` 导出单进程合成状态。`node --test examples/atlas/test/*.test.mjs` 覆盖内容绑定、身份与权限版本、过期、重复键和回执恢复。它不是数据库事务实现；文件快照与内存操作不能保证多进程并发或断电时的外部一致性。`confirm` 是程序接口，本示例没有把预览确认接成生产浏览器授权流程。

到这里，写操作已经拥有独立于模型表达的安全边界。后续开放 Agent 决策时，这些检查仍由执行器负责；Agent 可以提出保存建议，不能通过多说几次“已确认”使它变成授权。
