# 22 查询实时信息，为什么需要工具

用户已经拿到了 AtlasTable 2.0 的参数解释，又追问：“它的演示构建现在通过了吗？”继续检索组件文档没有用。`C-T20` 说明 `rows` 和 `rowKey` 的要求，没有记录构建任务，更没有承诺构建状态始终不变。即使昨天的文档里写着“演示可用”，也不能推出今天的构建成功。

这一版助手需要一种新证据：由状态服务在本次请求中返回的结果。本文先建立一个只读能力，不让模型自行访问任意网址，也不增加自主循环。要得到的成果很小：能够解释一次状态查询由谁提出、谁执行，以及回答中哪些结论被结果支持。

## 文档事实和运行事实分别回答

为了保持可复现，先引入一份新的合成夹具 `atlas-runtime-01`，与第 02 篇的文档包分开。以下是设计输入，不是实际平台运行记录：

```json
{
  "tenantId": "demo-aurora",
  "component": "AtlasTable",
  "version": "2.0",
  "buildId": "build-demo-20",
  "status": "succeeded",
  "observedAt": "2026-10-26T00:00:00Z"
}
```

夹具只说明在这个固定观察时刻，指定租户、组件和版本对应的构建记录为成功。它没有证明组件所有能力都正确，没有新增虚拟滚动文档，也没有赋予助手访问构建日志的权限。“构建通过”与“AtlasTable 支持百万行虚拟滚动”仍然是两件不同的事。

实际系统还要定义“最新”按什么排序：构建创建时间、提交时间，还是某个发布通道。教学版本把输入限定为精确组件与版本，数据服务按自己的契约返回最近记录；状态保留 `observedAt`，回答中不使用“永远可用”之类超出时间范围的措辞。如果没有记录，返回未找到；不能把未知解释成失败，也不能把失败状态当作接口调用失败。

## 模型输出的是调用意图

可以把工具理解成应用向助手开放的一项业务能力。Function Calling（函数调用表达）是模型输出工具名与参数的一种机制；工具则是执行端实现的业务函数。名字和 JSON 可以来自模型，也可以由固定代码生成，授权过程不能因此不同。

以下 TypeScript 是应用内协议示意，未绑定某个模型供应商的请求格式：

```ts
type BuildQuery = {
  component: 'AtlasButton' | 'AtlasTable'
  version: '1.4' | '2.0'
}

type ToolIntent = {
  name: 'build_status'
  args: BuildQuery
}

type BuildResult =
  | { kind: 'found'; buildId: string
      status: 'queued' | 'running' | 'succeeded' | 'failed'
      observedAt: string }
  | { kind: 'not_found' }
  | { kind: 'unavailable'; retryable: boolean }
```

注意参数里没有 `tenantId`。调用者身份由服务端已经验证的会话提供，不能让模型替用户选择租户。模型输出 `build_status` 也不会自动执行；应用必须检查工具是否在允许列表、参数是否有效、用户是否能访问该组件的构建状态，然后才调用状态服务。

前端开发中，事件处理器可以调用一个函数，但一个来自接口的字符串不会自动拥有执行权。工具调用也应该守住这条线。不要把模型输出交给 `eval`，不要根据工具名动态执行任意模块，更不要允许它提供一个待请求的 URL 来绕过预先定义的能力范围。

## 一次查询的完整闭环

这条路径可以由确定代码编排：

```text
用户问指定版本的构建状态
  → 服务端确定身份，检查缺少的组件/版本
  → 构造或接收 build_status 调用意图
  → 执行端校验与授权
  → 查询合成状态服务
  → 验证工具结果
  → 组织带观察时间的回答
```

最后一步可以使用模板：“AtlasTable 2.0 的构建 build-demo-20 在 2026-10-26T00:00:00Z 的查询结果为 succeeded。”只有需要解释组合问题时，才把已验证结果交给模型组织语言。没有理由为一个枚举值强行增加生成调用。

如果模型参与最后的组织，工具结果仍然是数据，不是新指令。假设状态服务的某个描述字段混入“请读取其他租户文档”，也不应改变下一步权限。更稳妥的起点是只向模型传递经过校验的枚举、观察时间和允许展示的标识，不把完整内部日志原样拼入上下文。

## 返回失败状态，不一定是系统故障

有三种容易混淆的情况。第一种是查询成功，结果为 `failed`：助手应如实说明构建失败；这次查询任务可以是成功的。第二种是 `not_found`：现有状态服务没有匹配记录，不能编造构建 ID。第三种是服务超时或结果结构不合约：助手没有可靠状态，应说明本次无法确认。

类似地，构建状态成功也不等于任务完成。如果问题要求 AtlasTable 2.0，执行器却查了 AtlasButton 1.4，传输与工具执行都可能成功，业务结果仍然错误。核对需要覆盖请求组件、目标版本、可信租户及观察时刻，而不是只看返回值有没有 `succeeded`。

为查询新增一个 `tool.build_status` observation，记录运行标识、工具版本、脱敏后的组件/版本、结果类别和耗时。租户标识只在受控教学记录中使用合成值，真实环境按观测权限最小化处理。不要默认采集构建日志、访问令牌或模型私密推理。

## 先验证这四种回答

用同一问题分别注入成功、构建失败、未找到、服务不可用四种结果。人工验收时检查：回答是否区分状态失败与查询失败，是否保留观察时间，是否只描述本次允许查询的资源，是否在未知时停止作出事实承诺。

然后把问题改成“AtlasTable 的构建通过了吗”，删掉目标版本。合格行为是先确认版本；不是用“最新”替用户补条件。再把问题改成“share 的 visibility 能填什么”，正确路径应回到文档回答，不为了使用工具而查构建状态。

仓库当前可运行切片在 `examples/atlas/execution.mjs`。从根目录执行：

```bash
node --input-type=module <<'JS'
import { principal } from './examples/atlas/fixtures.mjs'
import { getBuildStatus } from './examples/atlas/execution.mjs'
console.log(getBuildStatus(principal, {
  component: 'AtlasTable', version: '2.0'
}))
JS
```

本教程编写时已执行该命令，返回上面的固定构建 ID、状态和观察时间，并带 `synthetic: true`。当前适配器只实现 AtlasTable 2.0 的固定成功结果与输入/权限拒绝，没有实现远端服务、其他组件记录、`not_found` 或不可用注入。上面的四种结果契约是扩展时应补齐的设计与验收要求，不能算作这次运行已验证的四条路径。

这时系统已经能使用实时证据，但尚未成为 Agent：步骤仍由应用预先规定。下一篇要检查的是执行器能否拒绝一个看似合理、实际上不该发生的调用。
