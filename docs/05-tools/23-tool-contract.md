# 23 工具描述是给模型看的，执行校验是给系统做的

模型已经能输出 `build_status`，参数里也确实写着 `AtlasTable` 与 `2.0`。是否就可以执行？如果当前用户没有查看该项目构建的权限，答案仍然是否定的。工具描述帮模型选择动作，执行校验决定系统允许什么，两者面对的是不同问题。

这一篇的成果是一份可以拒绝执行的契约。一个工具只展示成功路径，很容易让人误以为错误分支都是以后补的异常处理；对模型驱动的调用来说，拒绝不合法动作本来就是正常路径。

## 描述要能帮助选择，也要说清不适用范围

`build_status` 的描述不能只有“获取信息”。它应说明查询对象、输入范围、结果时效以及不做什么。例如：“查询当前已授权租户中指定组件、指定产品版本的最近演示构建记录；仅返回状态与观察时间，不启动构建、不读取日志，不证明组件参数能力。”

这段描述解决两个选择错误：用户问“组件有什么参数”时，不应该调用它；用户要求“重新构建”时，也不能把查询当作执行。同样，参数名用 `version` 而不是模糊的 `id`，可以减少模型传错数据的机会，但清晰描述仍不构成安全控制。

前端表单会限制输入长度、展示枚举选项，后端仍需重复校验。模型生成参数与浏览器提交表单一样，都位于不可信输入边界。所谓 schema（结构约束）能检查形状、类型和部分取值，不能证明会话权限或操作意图。

## 拒绝发生在调用业务函数之前

下面是未绑定框架的 TypeScript 校验示意。它刻意从 `unknown` 开始，而不是用类型断言把外部输入假装成合法值：

```ts
type BuildArgs = {
  component: 'AtlasButton' | 'AtlasTable'
  version: '1.4' | '2.0'
}

function parseBuildArgs(raw: unknown): BuildArgs {
  if (!raw || typeof raw !== 'object' || Array.isArray(raw)) {
    throw new Error('invalid_arguments')
  }
  const value = raw as Record<string, unknown>
  const keys = Object.keys(value).sort().join(',')
  if (keys !== 'component,version') throw new Error('invalid_arguments')
  if (value.component !== 'AtlasButton' && value.component !== 'AtlasTable') {
    throw new Error('invalid_arguments')
  }
  if (value.version !== '1.4' && value.version !== '2.0') {
    throw new Error('invalid_arguments')
  }
  return { component: value.component, version: value.version }
}
```

拒绝额外字段很有意义。即使模型添加了 `tenantId: 'demo-bay'` 或 `endpoint`，执行器也不会悄悄接受这些超出能力范围的参数。随后用可信身份检查资源访问，再查预算、请求截止时间和工具可用性。没有通过这些检查时，业务函数的调用计数应为零。

版本属于允许枚举也不意味着一定存在相应构建。校验只回答“这个查询是否合约”，记录是否存在由数据服务回答。不要把不存在的 AtlasTable 1.4 构建记录从别的版本补出来，也不要让版本字符串比较替代产品版本规则。

## 返回值也需要契约

工具接入的是另一个边界。即使调用的是自己写的服务，版本部署不一致、代理错误或测试桩配置错误，也可能返回 HTML、缺失时间或不认识的状态。执行器必须在结果进入模型前校验，而不是“外部结果都可信”。

可以把执行结果按两层表达：

| 层 | 示例 | 处理含义 |
| --- | --- | --- |
| 执行结果 | `ok`，携带已验证的 `BuildResult` | 可以交给回答层解释 |
| 参数失败 | `invalid_arguments` | 修改输入；不自动重试同一输入 |
| 授权拒绝 | `forbidden` | 停止；不让模型换租户试探 |
| 服务故障 | `unavailable`，标注可否重试 | 在剩余预算内考虑有界重试 |
| 返回违约 | `invalid_result` | 隔离结果并报告；不作为事实 |

用户可见信息与内部排障信息也要分开。对越权请求，返回统一的无权访问说明，不披露隐藏资源是否存在、文档名称或内部服务路径。受限审计可以记录拒绝类别和允许的资源摘要，但不能把禁止读取的原文作为“调试便利”写入普通 trace。

## 合理的参数也可能是错误的动作

假设用户问“AtlasButton 1.4 的 loading 会禁止点击吗”，模型调用 `build_status({ component: 'AtlasButton', version: '1.4' })`。参数合法，用户也可能有查询权限，但动作与任务无关。执行端最少要检查工具是否在当前任务允许的动作集合中；评测还要检查工具选择是否帮助完成问题。

授权允许和任务必要不能混为一谈。前者是必须阻断的硬边界，后者可能是可以记录、反馈的质量问题。重复调用一个合法只读工具虽然未越权，也可能耗尽时间与预算；预算控制不能只针对危险写操作。

对于以后增加的写工具，还需另有用户确认。schema、资源授权、任务范围与用户确认分别回答：参数是否合法、用户能否操作资源、当前任务是否需要这个动作、用户是否批准了这次具体变更。四项不能相互替代。

## 用“不应该调用”验证执行器

给工具适配器加一个测试计数器，然后输入额外租户字段、错误版本类型、未知工具名和已撤权身份。这四项都应被拒绝，且适配器调用次数保持零。再让适配器返回不在枚举中的 `status: 'probably_ok'`，预期执行器返回 `invalid_result`，模型不应看到它作为已验证事实。

最后保留一个成功查询和一个 `not_found` 查询，防止过严校验把所有请求都拒绝。测试是否通过不能只靠抛了异常；还要验证没有越过业务调用边界、错误类别稳定、用户提示不泄露隐藏信息。

仓库 `examples/atlas/execution.mjs` 的实际 `getBuildStatus` 比本篇设计更窄：只接受 AtlasTable 2.0、拒绝额外字段和无权限身份，返回固定合成结果。可用 `node --test examples/atlas/test/*.test.mjs` 验证这些已实现边界。`not_found`、外部结果 schema 校验与不可用恢复是接入真实适配器前仍需实现的要求，本文没有把它们描述成已经完成的远端调用测试。

这份拒绝矩阵会成为后续工作流和 Agent 共用的底座。把执行器写稳后，是否让模型选择下一步就成为可比较的产品决策，而不是一次无法控制的函数调用。
