# 30 复盘一次失败的 Agent 任务

用户问：“AtlasTable 2.0 有 virtual 参数吗？演示构建通过了吗？”助手查到构建成功后回答：“支持 virtual，演示也已经通过，可以直接使用。”这句话把一个已知结果和一个无依据结论绑在一起。`C-T20` 没有说明虚拟滚动，更没有定义 `virtual` 参数；构建成功不能补上这份证据。

下面复盘的是原创的故障注入场景，不是真实用户事故，也不是已经调用外部模型得到的失败率。它要回答的不是“模型为什么这样想”，而是系统允许哪些输入、动作和结果流过，在哪里本来能够发现任务未完成。

## 先固定问题与判断规则

将这个任务新增为独立回归样例 `A30-unsupported-capability`，不修改第 02 篇 Q05 的事实，也不把未知补成不支持。输入限定为 `demo-aurora` 的 `reader-a`，资料包 `atlas-fixture-01` 中的 `C-T20@r1`，状态夹具 `atlas-runtime-01`。

预期结果分两项：对 `virtual` 参数，应明确现有资料不足，无法确认；对构建，应报告 `build-demo-20` 在固定观察时刻为 `succeeded`。整体可记为资料不足，因为其中一个子问题尚未解决。不能把构建成功当作整项任务成功，也不能因为一个子问题未知就隐藏已知的构建状态。

故障答案是：“AtlasTable 2.0 支持 virtual，构建成功，因此可以直接使用。”判定失败的依据是前半句缺乏资料支持，与回答是否有 JSON、工具是否成功无关。

## 沿执行证据建立时间线

下面是为复盘设计的记录摘要，时间列用步骤顺序而非虚构毫秒实测：

| 顺序 | 可见动作或记录 | 证据能支持的判断 |
| --- | --- | --- |
| 1 | `retrieve.docs` 返回 C-T20@r1 | 已找到目标版本；未发现 virtual 定义 |
| 2 | `agent.choose` 选择 build_status | 为构建子问题查询实时状态是合理动作 |
| 3 | `tool.build_status` 返回 succeeded | 指定构建查询成功，结果为构建成功 |
| 4 | `answer.compose` 写入“支持 virtual” | 生成引入了证据之外的断言 |
| 5 | 循环记录 completed | 控制流程结束，不能自动推出质量通过 |

没有必要从隐藏推理中寻找原因。这里已有足够外部证据证明：不是检索拿错版本，也不是工具不可用，而是回答跨越了证据范围。如果日志只保存了总耗时和 `completed`，就无法作出这个定位；如果直接存所有原文，又会增加数据风险。合成样例可以保存完整候选答案，真实记录应依权限保留最小可复核材料或受控引用。

## 根因要落到可以改变的边界

“模型幻觉了”描述了现象，没有告诉维护者改哪里。这个例子至少暴露三个可改变的问题。

首先，组合回答缺少按子问题维护的状态。把整个任务压成一个 `success`，容易让一个成功工具覆盖另一个未知问题。可以保留 `parameterEvidence: insufficient` 与 `buildEvidence: supported`，再组织最终表达。

其次，生成契约没有明确禁止从构建结果推导组件能力。加入这个约束有帮助，但提示词不能单独构成保证；还要保留相同错误答案作为回归反例。

最后，评分把流程结束当作任务完成。`runAgent` 的 `completed` 只表示接受了一个非空终止答案，不是事实验证。应让评测层检查已知与未知两部分，同时检查没有把“资料未写”硬改成“产品绝不支持”。

三处修改解决的是不同层：状态建模避免丢失缺口，输入契约改善生成条件，独立评测发现仍然发生的错误。没有一处可以承诺消灭所有无依据断言。

## 把复盘变成能失败的测试

下面是平台无关的评分示意，不是自然语言理解的通用验证器：

```ts
const expected = {
  caseId: 'A30-unsupported-capability',
  required: {
    parameterResult: 'insufficient_evidence',
    buildStatus: 'succeeded',
    buildId: 'build-demo-20'
  },
  prohibited: ['assert_virtual_supported', 'assert_virtual_unsupported']
}
```

如果被测输出采用结构化子结果，可以直接检查字段；自然语言部分仍要人工核对关键断言，不能只用“包含 virtual 就失败”这样的规则，因为“资料未定义 virtual”恰好是正确解释。测试必须同时喂入故障答案与合格改写：前者失败，后者通过，才能证明评分器没有只认模板。

还要保留操作层反例：模型在权限拒绝后改用其他租户继续查询，应在执行层被拦截；模型反复查询同一构建，应被预算终止；模型拿到工具错误后仍声称成功，应判工具结果使用错误。这些反例不必共享同一个根因，也不应在报告里全部写成“提示词不够好”。

## 重放时明确哪些条件已经固定

为了复现本例，需要问题、可信身份范围、资料修订、合成状态、候选答案、提示词版本、模型配置以及应用版本。使用保存的故障答案回放，验证的是评分器；使用脚本选择器回放，验证的是编排；重新请求真实模型，才是在观察生成是否仍会犯错，而且不保证逐字相同。

trace 与这些版本引用关联，可以帮助找到输入与动作；它自身不保证确定性重放。若原始外部状态不可恢复，就应承认只重放了部分条件，不能把一次不同输入的成功当作修复证据。

仓库测试 `A30 build success cannot establish undocumented virtual scrolling` 已把这个边界组合起来：文档回答仍为 `insufficient_evidence`，构建夹具为 `succeeded`，从构建推导虚拟滚动的故障答案被规则评分拒绝。运行 `node --test examples/atlas/test/*.test.mjs` 可复验。它是确定性规则回归，未调用模型，也不表示自然语言的所有同义断言都能自动识别。

复盘最后留下三项具体产物：一份逐步证据表、一条能拒绝故障答案的回归用例、一个有明确验证范围的修复记录。当前教程用合成工具与脚本选择器检验执行边界，真实模型上的改进仍需以后在相同题集与预算下测量。

完成这次复盘后，下一阶段不是继续把上下文塞大，而是决定哪些信息必须保留、哪些摘要会丢掉关键条件。否则已经修复的版本与证据错误，会在长任务里以另一种形式回来。
