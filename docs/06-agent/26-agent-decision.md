# 26 固定流程的分支越来越多，下一步该由谁决定

“把按钮迁到 2.0，并告诉我演示是否通过”适合固定工作流。但用户也可能这样问：“这个等待状态看起来不对，帮我查清楚。”组件、起始版本和问题性质都不明确。助手可能先问版本，也可能在用户给出代码后发现参数属于另一个版本；得到资料后，还可能需要比较变化。

这个任务暴露了新的选择问题：哪些信息缺失，要先取得哪一份证据，什么时候应停下来询问用户。让模型在少量允许动作中选择下一步，可能减少预先枚举的路径；但它也可能多查无关资料、忽略已有答案，甚至在权限拒绝后继续试探。本篇先做引入决策，不把 Agent 当作系列必经的毕业形态。

## 增加分支与开放选择不是同一件事

固定工作流由代码规定步骤和分支；Agent 在限定范围内根据当前结果动态选择动作。这个区别与有没有调用模型、用了几个工具无关。一个模型负责提取版本号、代码负责按条件分支的系统，仍然可以是工作流。这里沿用 [Anthropic 对 workflow 与 agent 的架构区分](https://www.anthropic.com/research/building-effective-agents)，核对日期为 2026-10-26；只引用概念区别，不沿用该文中的具体工具版本。

前端路由可以有很多分支，但浏览器不会因为路由多就自行决定用户下一站。同样，复杂度本身不是自主选择的收益证据。先问三个更具体的问题：路径是否真的无法预先确定；每一步是否能从外部结果得到反馈；选错后是否有可控的停止边界。如果只是接口响应慢，Agent 不会解决性能问题；如果资料不存在，多想几轮也不会产生证据。

## 先缩小允许动作，再讨论智能

给 Atlas 助手的第一版动态选择只保留五类动作：

| 动作 | 有什么作用 | 必须守住的范围 |
| --- | --- | --- |
| `retrieve_docs` | 按已知约束查资料 | 可信身份过滤，不能自选租户 |
| `compare_versions` | 比较已授权的指定版本 | 缺少版本时先澄清，不外推 |
| `build_status` | 查询演示构建 | 只读，要求组件和版本 |
| `ask_user` | 请求决定性缺失条件 | 暂停任务，不在等待时继续乱试 |
| `finish` | 提交有依据的答案或不足说明 | 关键断言可查证 |

这是教学动作目录，不是某个 SDK 强制规定的类型。`save_migration_draft` 暂不进入自主循环；需要保存时由用户进入上一篇的预览确认路径。`share`、`getLocation` 仍然只是文档里的接口名字，没有获得执行授权。

给模型一个动作列表的同时，也要告诉执行器同一列表。若模型返回 `read_all_tenants`，服务端直接拒绝未知动作，不能把它当作一个“计划步骤”尝试实现。资料中的命令、工具返回的文字或历史摘要，都无权扩大这个集合。

## 用失败样例写决策记录

先挑两个任务。任务 A 是明确的按钮迁移，固定流程已经知道怎么做；任务 B 是缺少版本的等待状态排查，需要先澄清。写下引入 Agent 的假设：“动态选择能在不同信息缺口下少做无关查询，同时保持版本正确与权限隔离。”这是一条待验证假设，不是已经实现的收益。

记录至少应有：基线流程、候选动作、预期收益、最坏失败、预算及撤回条件。最坏失败不能只写“回答不准确”，应具体到“把 2.0 的 pending 建议给 1.4 用户”“权限拒绝后继续查询其他入口”“资料不足却宣称问题已解决”。这些都能转化为后续评测题。

同时保留一个 Agent 更差的预期例子：资料已齐的 Q03，本来一次有依据回答就够，动态选择却连续查询构建再检索两遍。即使最终答对，也增加了耗时与费用。如果这种情况普遍存在，就把明确任务留在固定工作流，只把少数不确定任务送入受限选择路径。

## 什么时候不应进入循环

缺少用户必须决定的版本时，澄清通常比猜测更合适；没有访问权限时，应停止而不是寻找绕行路径；同版本权威资料冲突时，需要维护者核实，而不是让模型投票选一个胜者。Agent 的自由度只解决动作选择，不解决事实不存在、身份不足或授权缺失。

这篇的实践是写一页决策记录，为每个候选任务给出“固定流程”“受限选择”或“人工处理”之一，并写出能够改变这个选择的证据。验收时看记录能否被实验推翻：如果无论测出什么结果都坚持使用 Agent，它就不是工程决策，只是预设结论。
