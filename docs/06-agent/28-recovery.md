# 28 任务中断以后，如何安全继续

助手查询了构建状态，还没来得及把答案发给用户，进程重启了。重新读聊天记录只能知道用户问了什么，未必知道工具有没有执行；读取 trace 也未必得到完整状态，因为上报可能延迟、被采样或失败。若以后加入写操作，从头再跑还可能产生重复草稿。

恢复的起点不是“让模型回忆刚才做到了哪里”，而是应用保存了哪些已经确认的状态。本篇区分消息、任务与外部操作，建立能验证的检查点边界；示例采用单进程文件快照，不把它包装成分布式任务系统。

## 三种记录不能相互替代

会话消息服务于交互，里面可能有用户问题和已经展示的回答。任务状态负责说明当前阶段、已经完成的步骤、剩余预算和待确认条件。外部操作状态负责说明某项副作用到底有没有完成，例如某个幂等键是否已经保存草稿。

聊天历史里有“正在保存”不代表已保存；任务阶段写着“调用中”也不能证明没有执行。恢复必须针对不同状态查询正确来源。trace 帮助排障和关联，但不是事务日志，也不是任务状态库。即使观测平台恰好保存了工具结果，也不应让恢复依赖它是否被采样保留。

一个检查点至少应记录如下信息，以下为设计示意：

```ts
type Checkpoint = {
  taskId: string
  attempt: number
  nextStep: number
  ownerScope: string
  permissionRevision: string
  inputVersion: string
  deadlineAt: number // 服务端 Unix 毫秒时间，恢复不重置
  completedActions: Array<{ callId: string; resultRef: string }>
  pendingOperation?: { idempotencyKey: string; state: 'outcome_unknown' }
  budgetUsed: { choices: number; toolCalls: number }
}
```

输入与代码版本也重要。旧检查点里的 `loading` 建议来自哪个资料修订？恢复时如果索引已经更新，应继续原证据快照还是重新验证？不能由序列化文件存在就得出答案。教学方案先固定资料包与任务版本，遇到不兼容修订停下来重新评估，不悄悄复用旧结论。

## 保存时机决定恢复能保证什么

对只读查询，可以在取得并校验结果后保存检查点，再进入下一轮。若在查询后、保存前崩溃，恢复可能重复读取一次；这仍有成本与时效问题，但不会创建业务记录。若检查点已保存，则下一轮应复用已确认结果，不无条件重新查询。

对写操作，窗口更危险：外部服务提交成功，但本地还没记下结果。无论先记“准备写”还是先调用，都不能凭一个本地布尔值消除两端之间的不确定性。需要第 25 篇的幂等标识与操作状态查询，恢复时先核对该操作是否完成，再决定重试。

文件快照可以用“写临时文件，再替换目标文件”减少读到半截 JSON 的风险；它不提供跨进程的任务锁、事务隔离或远端操作原子性。多个工作进程同时恢复一个任务时，真实系统还需要所有权租约、版本比较或数据库锁，防止两个执行器同时推进。课程的单进程 mock 不声称解决这些问题。

## 重新进入任务，先重新授权

检查点保存了上次的身份范围，不意味着权限永远有效。恢复请求必须重新确认当前身份，再核对任务所属用户、租户和当前权限。旧任务有访问权，今天权限被撤回，不能靠快照中的旧资料继续回答。

确认也不自动跨恢复。保存草稿的预览可能已经过期、内容被修改或权限版本改变；需要重新展示并取得对应确认。先前的确认只对当时的具体操作有效，不是给后续所有步骤的永久许可。

用户可能只想查看已完成结果，不想重新运行。恢复入口应分清“查询任务状态”“继续未完成任务”和“重新开始一个新任务”。最后一种需要新的任务标识，不应偷偷复用旧幂等键；第二种则应保留已经消耗的预算，不能每次重启都把最大步数归零。

## 两次执行，两条 trace，一个任务

给每次执行尝试新建 trace，并使用相同 `taskId`、递增 `attempt` 和明确的检查点标识关联。恢复后的新调用不是已经结束的旧进程子调用，不要为了图上看起来连贯而伪造仍在运行的父 span。

```text
task-demo-28
  trace-A / attempt-1 → 查询完成 → checkpoint-1 → 进程中断
  trace-B / attempt-2 → 校验 checkpoint-1 → 使用已有结果 → 完成
```

上述关系表达的是任务连续性。若需要跨服务传播活动请求上下文，按实际追踪协议传递；若是几小时后恢复，则任务 ID 与检查点关联更能说明事实。记录恢复原因、重用动作数、重新执行动作数与停止原因，不收集模型私密推理来填补缺失状态。

这套关联还要区分两条实际代码路径。本篇的恢复测试运行 `examples/atlas`，检查业务快照、再授权与绝对截止时间；第 27、30 篇的新观测演练运行 `examples/atlas-observability`，包含每轮按状态选择 read_docs、build_status 或 finish 的真正受限循环，检查 SDK 导出的步骤与停止证据。新循环也检查绝对 `deadlineAt`，但尚未实现业务检查点保存与恢复；报告明确 `resumeSupported: false`。`agent-compare` 先运行重复策略，再运行修正策略；后一次即使沿用 taskId、递增 attempt，也是一项独立回归，不是从前一次的 nextStep 继续。不能拿它的新 trace ID 推断旧工具已经执行或没有执行。

将来连接两者时，每次尝试的 trace 可以携带 `taskId`、`attempt`、`checkpointId` 和 `deadlineAt` 摘要，但真实恢复仍读取业务快照。检查点标识用于定位受控记录，不应直接导出含权限材料的完整快照。读取 trace 的权限也不能自动授予继续任务的权限；新一次继续操作仍须重新授权。

## 做一次真正可控的中断演练

仓库合成运行时的 `saveCheckpoint`、`loadCheckpoint` 与 `runAgent` 支持这个演练：第一轮执行只读构建查询，在 `onCheckpoint` 收到状态后模拟进程退出；第二次加载同一状态，让选择器直接结束。测试断言应同时满足：尝试数增加、已保存 observation 保留、工具调用累计仍为一次。

另一个演练用 `DraftStore.snapshot()` 保存确认回执，重建 store 后按原幂等键 `lookup`。它验证回执存在时能找回同一草稿，不意味着已经模拟“文件落盘前突然断电”或多进程竞争。当前循环保留累计步数、工具次数、合成选择额度和绝对截止时间 `deadlineAt`。首次创建时用服务端时间加 `deadlineMs` 得到截止时间，保存检查点时一起落盘。恢复后即使传入更大的 `deadlineMs`，也只使用原 `deadlineAt`；已到期的未完成任务在再次调用选择器之前以 `time_budget` 停止。缺少或损坏截止字段的旧检查点以 `checkpoint_deadline` 拒绝，不能悄悄补发一份预算。

新增测试将首次截止时间固定为 110，保存检查点后把时钟推进到 110，再用 100000ms 的参数恢复；预期选择器调用数仍为零、工具次数仍为一次。另一条测试在 109 恢复、选择到 111 才完成，同样拒绝超时完成。这里采用可信服务端的 Unix 毫秒时间；生产环境仍需管理时钟回拨和跨机器时间一致性，本例不实现分布式时钟或任务租约。检查点必须来自应用受控存储，不能由模型或请求正文提供。相关源码在仓库 `examples/atlas/execution.mjs`，统一验证命令为：

```bash
node --test examples/atlas/test/*.test.mjs
```

再把恢复身份的权限清空，预期在继续选择动作之前拒绝。最后故意删除快照，正确结果应是“无法从该检查点恢复”，而不是让模型凭会话猜测之前是否写入。恢复能力的验收不是能多跑一次，而是知道什么可以重用、什么必须核对、什么目前无法保证。
