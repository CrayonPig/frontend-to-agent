# 06 流式回答的状态，不只有 loading

用户问 Q03，页面开始逐字显示“Atlas UI 1.4 使用 loading……”。这时他发现选错版本，马上改问 2.0。旧请求晚到的片段如果继续拼进新答案，页面会出现一个根本不属于任何请求的混合结果。即使后台两次回答都正确，前端仍然把任务做错了。

流式输出让等待过程可见，也把“响应还没完成”变成持续存在的状态。本篇要解决的是结果归属与终态，而不只是让文字更快出现。

## 文字片段和最终结果分开存

一次请求至少经历等待、接收、完成，也可能进入失败或取消。接收状态里的文字是候选草稿，不能因为看起来像完整句子就成为经过验证的答案。特别是结构化输出，半段 JSON 不能通过最终 schema，也不能作为执行参数。

```ts
// 界面状态设计示意；不绑定 React 或某个流协议。
type ViewState =
  | { phase: 'idle' }
  | { phase: 'waiting'; requestId: string }
  | { phase: 'receiving'; requestId: string; draft: string }
  | { phase: 'completed'; requestId: string; result: unknown }
  | { phase: 'failed'; requestId: string; draft: string; error: string }
  | { phase: 'cancelled'; requestId: string; draft: string }
```

最终实现中的 `result` 应替换成已校验的 `TaskResult`；这里突出的是草稿与结果不共享一个字段。页面可以把草稿标成“生成中，尚未验证”，收到服务端明确的完成事件之后才切换到最终展示。若发生中途断连，保留草稿可以帮助用户理解发生了什么，但不能同时显示“回答完成”。

对于可疑引用或需要严格隐藏的内容，先流式发送“正在核对资料”等状态事件，等验证后再发完整答案，也是一种合理选择。流式不是必须提前暴露每个生成 token 的产品义务。

## 用请求标识挡住迟到事件

每个事件应带上服务端认可的请求标识；浏览器还可以用本地递增序号防止提交阶段的竞态。核心规则不是“取消了就不会来”，而是“不是当前请求的事件不能改变当前视图”。

```ts
// 简化示意；实际 reducer 还需按 phase 验证合法转移。
function acceptEvent(state: ViewState, event: { requestId: string }) {
  return 'requestId' in state && state.requestId === event.requestId
}
```

同一请求内也要保护终态：一旦变成 `completed`、`failed` 或 `cancelled`，迟到的片段不应让状态倒退为 `receiving`。如果传输层可能重放事件，还需要单调序号去重。这里只在应用层提出约束，不能假定每种供应商流协议都自带同样的字段。

测试可以人为安排事件顺序：A 开始、A 片段、B 开始、A 完成、B 片段、B 完成。最终页面必须只有 B 的结果。再把 B 完成后插入一个 B 片段，结果也不能改变。这类确定性测试比依赖网络恰好变慢更可靠。

## 停止显示与停止执行不是一件事

浏览器可以用 `AbortController` 终止本地等待，并把取消信号沿服务端适配层传递。Node 的 `AbortSignal` 提供信号表达和超时组合能力；具体操作是否响应信号，仍由被调用 API 决定。[Node.js 官方 API](https://nodejs.org/api/globals.html#class-abortcontroller)，核对于 2026-10-26。

用户点击停止后，可以立即停止更新草稿，但不能据此断言模型没有生成更多内容、没有产生费用，或后续工具从未执行。取消事件与远端完成回执可能交错；本地 `AbortError` 只能证明本地等待路径被取消，不能证明远端业务回滚。

对于当前只读问答，页面可提示“已停止等待，部分内容未验证”。对于将来的模拟写入，则必须查询操作状态后才能说明是否生效。这也是为什么不要把“取消”设计成一个通用的“什么都没发生”状态。

## 完成事件需要什么证据

服务端收到供应商的流结束，不应立即透传一个无条件的成功。它还要检查结束原因：是否正常结束、输出是否截断、是否拒答、结构是否完整，随后执行第 05 篇的校验。通过后再发应用层完成事件。

一条教学事件序列可以是：

```text
started(requestId)
delta(requestId, sequence=1, text="Atlas UI 1.4…")
delta(requestId, sequence=2, text="…loading 与 disabled…")
completed(requestId, validatedResult)
```

如果最后变成 `failed(requestId, code="invalid_output")`，前两段文字仍然只是草稿。不要把“最后一个字已到达”与“最后一道业务校验已通过”当成同一时刻。首个 token 耗时、首个可用信息耗时和完整任务耗时，也因此是不同指标。

实际传输还可能把一个字符或一个事件切成多个网络块。客户端应使用正确的文本解码和事件缓冲，不假设每次读取就得到一个完整 JSON。本文不绑定 SSE 或某个 SDK；引入具体协议时，应单独验证分片、重连和结束语义。

## 用可控时序验收，而不是看动画

准备五组时序：正常完成、首段之前失败、输出一半断开、用户取消、旧请求迟到。每组都检查状态最终停在哪里、草稿是否被误标为答案、是否还能继续覆盖新问题。仓库示例已提供 NDJSON 分块交互与正常完成事件的 HTTP 测试；这五组浏览器时序仍是待执行的人工或扩展自动化验收，不能冒充已覆盖。真实供应商流式接入还需增加适配层测试。

可用性的目标也应具体：等待状态能解释当前进度；失败后用户知道是否可以重试；取消后不继续写入页面；完成结果可回溯到请求标识。更快的打字动画不满足其中任何一条。到这里，问答链路已经能表达发生了什么，下一步是判断那些顺利完成的答案究竟有没有变好。
