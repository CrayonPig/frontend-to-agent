# 04 把第一条请求接进我们的应用

现在有了 Q03 和 C-B14，最直接的实现似乎是在页面里加一次模型请求。这样能少写一个接口，却会把凭证、身份判断和文档选择一起放进浏览器。浏览器中的代码与请求参数都由客户端控制，无法承担这些责任。

第一条可交付的调用链，应当是浏览器提交任务，应用服务确认范围，模型适配层生成候选结果，最后由应用服务返回。即使先用 mock，也要把这几个接缝放在正确的位置。否则日后替换供应商时，往往连页面状态和权限判断也得一起改。

## 请求里不接受自报的权限

页面提交的问题和目标版本是用户意图；当前用户、租户与权限范围则来自服务端验证过的会话。两者不能混成同一份可信对象。

```ts
// 接口设计示意；字段校验与会话读取由应用实现。
type AskInput = { question: string; targetVersion?: string }
type Principal = {
  userId: string
  tenantId: string
  permissionRevision: string
}
type CallContext = {
  requestId: string
  principal: Principal
  signal: AbortSignal
}
```

如果客户端额外发送 `tenantId: 'demo-bay'`，服务端不能因此切换租户。对于本教程的本地示例，可以固定注入 `reader-a / demo-aurora` 作为**合成身份夹具**，但必须把它标成演示实现；它不等价于登录系统。真实应用还需要会话验证、资源授权、请求体大小限制和访问预算。

服务端先验证输入：问题是否为非空字符串、长度是否合理、版本字段是否为允许的格式。格式校验通过后，才进入任务逻辑。Q07 缺少版本不是网络错误，可以返回 `needs_clarification`，不必花一次模型调用去猜默认版本。Q08 明确请求其他租户资料时，服务端应按真实身份拒绝，也不必先读取隐藏文档让模型作决定。

## 适配层只暴露本应用需要的能力

供应商往往有不同的请求字段、流事件和结束原因。页面不需要认识所有这些差异。先定义一个很窄的接口，减少变化向外扩散：

```ts
// 教学契约，尚未绑定外部 SDK。
interface ModelAdapter {
  complete(input: {
    instruction: string
    question: string
    evidence: { id: string; version: string; text: string }[]
    signal: AbortSignal
  }): Promise<{
    text: string
    finish: 'complete' | 'truncated' | 'refused'
    modelVersion: string
    usage: { inputTokens: number; outputTokens: number } | null
  }>
}
```

这里故意保留 `usage: null`。mock 没有真实模型用量，就应明确未知，不能把字符串长度当实测 token 数。适配器将供应商响应转换成内部形态，但不负责决定用户是否有权读文档，也不应吞掉原始错误类别，只返回一个含糊的空字符串。

这和前端的数据访问层很像：调用方依赖稳定接口，底层可以替换实现。失效的类比是“接口稳定就等于结果稳定”。适配器可以统一结构，却不能让不同模型有相同知识、拒答行为或准确性。更换实现之后，第 07 篇的同题回归仍然要运行。

## 让一次调用可被找回来

服务端为每次到达的请求生成 `requestId`，响应成功或失败都带回它。日志记录任务所需的最少关联信息：请求标识、合成用例 ID、资料修订、适配器版本、结果类别、错误类别和耗时。此时不必先接观测平台；一个受控的本地记录就能帮助定位。

下面是服务流程示意，函数名表示责任，不是已经安装的库：

```text
生成 requestId
→ 解析请求体并验证
→ 从服务端会话得到 principal
→ 判断任务范围与目标版本
→ 选择 principal 可访问的资料
→ 调用 adapter.complete
→ 检查结束原因、解析输出、验证结果
→ 返回 { requestId, result }
```

模型凭证只放在服务端进程的环境或密钥管理系统中，不带浏览器可暴露的构建变量前缀，不写入响应、文档或 trace。第一版使用 mock 不需要任何模型密钥；以后接真实服务时，替换的是适配器，不是把密钥补进页面。

注意两种 ID 的区别：`requestId` 标记某次 HTTP 尝试，用户重复点击可能产生两个；`taskId` 以后用来关联同一个逻辑任务的恢复。现在不要为了“串得起来”把所有用户都放进同一个固定请求 ID。

## 用固定答案验证管道，不用它证明智能

本地 mock 可以对 Q03 返回正确的 `loading`、`disabled` 说明，也可以按测试参数返回损坏 JSON、延迟或截断。固定输出的价值是让故障可重现：例如修改一次校验器后，所有测试仍能检查同一错误输入。

仓库提供 `node examples/atlas/server.mjs` 启动回环地址上的演示，以及 `node --test examples/atlas/test/*.test.mjs` 执行检查。当前规则适配器没有通用的损坏 JSON/截断故障开关；这些是后续外部适配器需要扩展的测试。使用示例时，应重点检查四条路径：合法题目收到对应的结果及运行标识；版本缺失得到澄清；伪造身份不能获得其他租户资料；适配器失败不会把内部错误或凭证原样返回。示例入口与最终命令统一列在[交付说明](../README.md)，不要把本篇的架构伪代码当作完整服务程序。

一个常见误判是：mock 回答正确，所以真实模型接入也算完成。实际上目前只证明了数据如何穿过系统，以及边界是否在确定性代码里执行。真实模型的格式波动、事实错误和外部超时没有被这个成功用例消除。

可以把第一次调用的验收写得很具体：同一个错误请求能用 `requestId` 找到原因；结果中没有隐藏资料；页面看不到服务端凭证；更换 mock 输出无需改页面的数据类型。达到这些条件之后，下一篇才有明确位置放输入约束与输出校验。
