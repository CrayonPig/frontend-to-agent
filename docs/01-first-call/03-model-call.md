# 03 一次模型调用里发生了什么

把第 02 篇的 Q03 原样发给一个模型：“Atlas UI 1.4 提交中既要显示等待又要阻止点击，怎么设置？”模型可能很快写出一段代码。但 Atlas 是本教程虚构的平台；如果请求没有带上 C-B14，它就没有这份文档可查。回答得具体，只能说明它生成了具体的文字，不能说明它掌握了项目事实。

第一次调用之前，最值得理解的是信息从哪里来、经过了什么，以及什么并没有发生。这样看到一个错误答案时，才能判断应当补材料、改契约，还是处理调用故障，而不是统一归因于“模型不够聪明”。

## 三种信息，不在同一个地方

模型训练得到的能力，可以帮助它理解“等待状态”“禁用点击”这类语言与程序结构；当前请求携带的 C-B14，则提供 Atlas UI 1.4 的具体事实。应用保存的历史记录是第三回事：数据库里有昨天的对话，不代表今天的模型调用自动能看见它。只有应用选择并发送的内容，或者服务明确支持且本次引用的状态，才进入本次推理的输入。

可以把这三者写在同一张便签上：

| 信息 | 本例中的作用 | 不能据此保证什么 |
| --- | --- | --- |
| 训练形成的能力 | 理解参数解释、组织代码 | 不保证知道合成平台的内部版本 |
| 当前上下文 | 给出 C-B14 的参数事实与问题 | 不保证模型一定遵守或正确引用 |
| 应用存储 | 留存题目、回答、资料修订 | 不会自动成为模型的长期记忆 |

这与前端组件的 props 有相似处：组件只收到传入的数据，不能凭空读取另一个页面的状态。但类比到这里就要停。确定性组件在相同输入下可以有明确的计算规则，模型生成语言不能被当作同样的纯函数契约。

## 文本如何进入一次生成

模型通常不是逐个汉字理解和输出，而是先把文本编码为 token。token 是模型使用的文本单元，可能对应一个词、一部分词、标点或其他片段；划分由具体 tokenizer 决定。`AtlasButton` 看起来是一个名字，并不意味着它一定只占一个 token。中文字符数、JavaScript 的 `string.length` 与实际 token 数也不能直接画等号。

本系列只需要知道这个单位影响什么：输入长度预算、输出长度预算、部分供应商的计费和使用量记录。不要用“每个汉字恰好等于一个 token”来做硬限制。接真实模型时，应使用对应的计数工具或服务返回的用量；没有真实 tokenizer 的本地 mock 只能验证预算分支，不能提供真实 token 估计。

把一次请求展开，可以看到下面的生命周期：

```text
浏览器提交问题与目标版本
  → 服务端确认身份、选择 C-B14@r1
  → 装配任务说明、资料、问题和输出约束
  → 适配层发送请求，记录模型配置与请求标识
  → 模型处理输入，逐步产生输出 token
  → 适配层接收文本与结束原因
  → 服务端检查结构、版本和证据
  → 页面展示已完成结果，或说明失败/资料不足
```

在典型自回归文本生成中，模型根据已有输入和已经生成的内容继续选择后续 token，直到满足结束条件或遇到限制。生成策略会影响选择；采样可能使相同问题出现不同表述。即使减少采样变化，也不能把它当作事实校验器，或保证跨服务版本的输出逐字相同。这里的机制解释依据 [Hugging Face 文本生成文档](https://huggingface.co/docs/transformers/main/en/llm_tutorial)，核对于 2026-10-26；本教程不安装其 Python 运行栈。

## 上下文窗口不是随身数据库

上下文窗口是一次模型处理能够容纳的信息边界。实际输入、输出的限制及二者关系取决于模型和接口，接入时必须核对具体契约。为了理解预算，可以先用一张教学账单，而不是记住某个产品的数字：

```text
任务说明      预算 A
用户问题      预算 B
授权资料      预算 C
历史与工具结果 预算 D
预留输出      预算 E
```

如果把所有版本的组件文档都塞进去，C 会增长，留给输出的空间可能减少；如果不断追加历史，D 会增长。更麻烦的是，即便没有超限，无关版本也会制造干扰。窗口大只能说明装得下，不代表决定性事实一定被正确使用。

Q03 的第一版输入只需要 C-B14，不需要 2.0 的按钮说明，更不需要其他租户的资料。选择材料同时是在减少歧义和建立权限边界，不只是节约 token。等问题变成迁移比较，才需要一起提供 C-B14、C-B20，并明确哪个是来源版本、哪个是目标版本。

## 最小实验：把“知道”改成可检查的输入差异

先做三份手工请求包，暂不调用付费模型：A 只有 Q03；B 有 Q03 和 C-B14；C 有 Q03 和 C-B20。对每份包写出“可以获得什么结论”。A 应保留资料不足；B 能支持 `loading` 与 `disabled` 分工；C 虽然有按钮资料，仍不能支持 1.4 的用法。

下面是 B 的平台无关示意，尚不是任何供应商的 API 参数：

```ts
const request = {
  task: '按资料解释参数，不执行操作',
  question: 'Atlas UI 1.4 提交中如何显示等待并阻止点击？',
  targetVersion: '1.4',
  evidence: [{
    id: 'C-B14', revision: 'r1', version: '1.4',
    text: 'loading 显示等待图标；disabled 阻止 click；没有 pending。'
  }],
  unknownPolicy: '证据不足时明确说明，不用其他版本补齐'
}
```

实验的预期不是“B 一定答对”，而是 B 具备答对所需的材料，A、C 不具备。后续 mock 用来稳定触发成功、截断和错误分支；真实模型的准确性需要单独评测。把“材料充分”与“生成正确”拆开，才能解释为什么增加检索之后仍然要检查回答。

再试一个失败：假设输出到“将 loading 设置为”便因输出预算结束。收到的文字不是完整答案，不能因为连接正常结束就标记任务完成。保存结束原因、是否完整解析以及结果类别，会比仅保留整段文本更有用。

读完本篇，应能沿生命周期指出模型实际收到了哪份资料，以及截断、版本错配和事实错误分别在哪里被发现。下一篇把这条链路接进应用，但仍保留可替换的模型边界。
